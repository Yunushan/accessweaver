# Audit events, local profile imports and checkpoint verification

AccessWeaver provides a bounded event-chain format, a read-only segment verifier and an explicit Linux profile-import path with protected local intent/outcome recording, consented read-only JSONL export, an explicit profile-editing desktop with required recording and explicit recorded policy transactions. A separate [recorded-export command](RECORDED_AUDIT_EXPORT.md) adds access intent/outcome around a current stream snapshot. Broader user/administrator action coverage, protected storage on the other desktop platforms, retention acknowledgments and collector integration remain unfinished. The enterprise audit readiness gate remains missing.

## Verify a segment

Retain the complete starting and ending checkpoints through an independently trusted administrative or collector channel. Then run:

```text
accessweaver audit verify --events segment.jsonl --from retained-start.json --to retained-end.json
```

The command reads three regular files, snapshots at most 1,024 bytes per checkpoint and 8 MiB of event data, and uses one shared 15-second deadline for input reading and verification. It creates no profile directory, modifies no input, starts no engine and contacts no service. Paths, malformed input, reader errors and event contents are excluded from failure messages. A blocked file read returns a verification timeout; its one outstanding worker can remain blocked until process exit.

Success reports scope checkpoint-matched-segment, stream ID, endpoint sequences, record/byte counts and checkpointHashesMatched. Failure returns a nonzero exit status without partial-success JSON. An empty segment can match identical checkpoints and reports zero records.

Both endpoints are necessary. A retained ending checkpoint detects loss or rewriting up to that known head. Events after that checkpoint, or never collected, remain outside its proof. A retained starting checkpoint permits verification of a retained suffix after an earlier segment has been archived. Self-selected replacement checkpoints can make a rewritten chain match: neither a matching chain nor its producer fields establish OS identity, publisher trust or authenticity of the claimed action. Collectors must protect enrollment, transport and stored checkpoints independently.

## Initialize and record a reviewed profile import

Local recording currently supports Linux amd64/arm64. The audit directory must already exist, be empty and owned by the executing UID with mode 0700, and reside on persistent ext4, XFS or Btrfs. Each ancestor must belong to root or that UID, exclude group/world writes and avoid setuid/setgid modes; the final directory also rejects the sticky bit. Aliases and noncanonical/relative paths refuse. Ordinary shared temporary directories are unsuitable. Initialization creates a new random 32-byte actor pseudonymization key and genesis stream, syncing both private files and their directory before returning a checkpoint. Existing entries, partial initialization and existing permissions are preserved rather than repaired. The private .actor-key file is never included in command output, events, profile backups or metadata-only support reports.

```text
accessweaver audit initialize --directory /home/operator/.accessweaver-import-audit
accessweaver audit import --directory /home/operator/.accessweaver-import-audit --from trusted-genesis.json --to trusted-head.json --profile reviewed-profile.json
```

Initialize prints one canonical checkpoint line. Authenticate and retain it through the independent administrative/collector channel before using the stream. For the first import, both checkpoints name that genesis. Import requires the full retained genesis and exact latest head; it never infers a new head from journal contents. Opening the stream and every append recheck its private key and current OS/build producer. Changed keys, actor class, source identity or target require explicit independent reenrollment in another stream, with the earlier journal retained. No automatic replacement, upgrade migration, collector enrollment or checkpoint authentication is performed.

Import emits two canonical checkpoint lines: the synced intent head before any profile mutation, then the synced outcome head. Capture them in a new observation file and retain each complete line through the trusted channel; two lines together are not a single checkpoint file. An existing profile's updatedAt must exactly match its reviewed saved revision. A missing/zero revision creates only an absent profile ID. Stale revisions refuse while preserving the saved profile. No built-in profiles are seeded and no engine or OS networking operation starts. The ordinary data directory selection, controller exclusion, administrator profile-change guard and profile-store locking remain in effect.

Each attempt admitted after bounded input snapshots records profile.import with a fresh operation ID and intent, followed by completed, refused, canceled or indeterminate. Profile contents, IDs, names, arguments, paths and error details are excluded. Malformed profile JSON and policy/revision refusals produce redacted refusal records. Input-read failures and invalid/untrusted endpoints before admission produce no event or profile mutation. Creating a new profile directory/coordination files is part of the intent-covered operation; a refused save can leave those directories/locks in place.

Capacity for both records is required before dispatch. If the intent cannot be persisted or its complete checkpoint cannot be written, import does not start. A broken intent output channel gets no further output; a local refusal is attempted if storage permits it. Cancellation before dispatch records canceled; once profile mutation starts, outcome recording uses a separate cooperative 15-second context so caller cancellation cannot silently discard a known completion. Unknown write errors, unexpected operation panic and failed post-mutation audit/output are reported conservatively: profile changes may have occurred. There is no automatic retry or rollback. Preserve journal bytes and inspect current profile state before independent reconciliation.

Input snapshots share a 15-second read budget and cap each checkpoint at 1,024 bytes and the profile at 1 MiB. Native filesystem calls, fsync and stdout writes can still block until the OS returns; the contexts do not impose a hard whole-command deadline. A successful stdout write is an observation, not durable collector acknowledgment or proof of external checkpoint retention. Failed commands can emit valid checkpoints for refusal/uncertainty records, so checkpoint output alone is not an import-success result. Interrupted/partial output must not replace a previously retained complete checkpoint. Initialization/output failures and unknown journal tails require independent reconciliation, with no destructive reset supplied by these commands.

The explicit audit import path records live profile-import actions, and the separate audited desktop below records profile saves/deletes. Ordinary import and ui mutations have no producer and refuse under signed requireProfileAudit policy. Explicit policy transactions use the separate commands below. Engine/workflow actions and backup/support exports still require integrated event producers. The separate [export-recorded command](RECORDED_AUDIT_EXPORT.md) records explicit current-stream access; ordinary audit export remains unrecorded and broader managed audit enforcement remains incomplete. The other desktop storage backends, collector transport/acknowledgment, managed export-access recording and cross-stream upgrade/recovery acceptance remain required. These commands do not close the enterprise audit gate.

## Record an explicit policy transaction

Linux amd64/arm64 supports these separately invoked administrative commands. Prepare and independently review the signed document using the existing offline managed tools first. Initialize an existing empty root-owned mode-0700 audit directory on qualified persistent storage, outside /etc/accessweaver, and authenticate its administrator genesis through an independent trusted channel. Invoke the commands through the existing separately elevated root CLI or endpoint-management channel; keep the dashboard unelevated.

```text
accessweaver audit policy-install --directory /var/lib/accessweaver-policy-audit --from trusted-genesis.json --to trusted-head.json --input INSTALLATION.json --public-key BASE64
accessweaver audit policy-update --directory /var/lib/accessweaver-policy-audit --from trusted-genesis.json --to trusted-head.json --input ENVELOPE.json
accessweaver audit policy-rotate --directory /var/lib/accessweaver-policy-audit --from trusted-genesis.json --to trusted-head.json --input ROTATION.json
accessweaver audit policy-recover --directory /var/lib/accessweaver-policy-audit --from trusted-genesis.json --to trusted-head.json --input RECOVERY.json --public-key BASE64 --minimum-revision N
```

These commands call the existing managed.Install, Update, Rotate or Recover entry point only after the journal has durably appended intent and stdout has accepted its complete checkpoint. They retain fixed machine authority, administrator checks, signed trust pins, revision/acceptance history, writer exclusion, atomic publication and cleanup rules. They grant no privilege, select no alternate backend and accept no private signing key. Update and rotation derive trust from current protected native state; install and recovery require the independent public-key pin, and recovery requires a positive safe-integer revision floor. Ordinary managed commands and direct administrator/MDM writes are not automatically recorded. Signed requireProfileAudit governs profile changes only; it does not make these optional policy producers mandatory.

Inputs share a 15-second snapshot budget: 1,024 bytes per checkpoint and the existing managed document cap for the chosen transaction. Unreadable input, invalid flags/trust-pin syntax, mismatched retained heads and untrusted storage refuse before native dispatch. Signed-document verification remains inside the existing native operation. The stream reserves two records before dispatch and emits policy.install, policy.update, policy.rotate or policy.recover with a fresh operation ID. Actor/source metadata identifies the executing process, not the originating human or management server. Policy bytes, public-key values, key IDs, revisions, paths and native errors are excluded from events and checkpoint output.

A clean native return with the expected operation and committed true records completed. Any native error, missing/mismatched committed result or panic records indeterminate rather than guessing whether publication or cleanup occurred. A signal observed before dispatch records canceled; cancellation after native work starts does not erase a known completion or abandon the transaction. Filesystem/native calls and stdout writes have no hard whole-command deadline. Failed outcome append/output or journal close is also uncertain. Preserve the journal and both observed heads, inspect managed status and actual state, then reconcile independently before retrying. No automatic retry, rollback, rotation, destructive journal reset or tail adoption is provided. A valid result checkpoint alone does not mean the native operation succeeded; inspect command status and the verified outcome.

Stdout carries only canonical checkpoints. Use a new private observation destination and retain each complete line independently. Direct regular-file aliases of checkpoint/payload inputs, journal, actor key, existing fixed machine-policy values or coordination lock refuse. Shell truncation happens before the command starts and cannot be undone here; callers must also keep wrappers/pipes from forwarding into protected inputs. An administrator stream is separate from an ordinary-user stream. Source/actor/key/target changes require independently authenticated reenrollment, with previous streams retained. The added policy.update and policy.rotate action names require a verifier that recognizes this action table; earlier verifiers intentionally refuse them. Existing record encoding and hashes are unchanged.

Contract tests exercise all four actions, required intent/output admission, cancellation, publication/cleanup errors, panic, result loss, action identity, redaction and direct/hard-link output aliases. Policy callbacks mask any inherited profile intent, without revoking an outer profile callback. The [33c7737 hosted Linux evidence](qualification/33c7737d97cd-linux-recorded-policy-audit.json) verifies a real recorded update and administrator export before the ordinary-user required-profile-audit roundtrip on both amd64 and arm64. This establishes those source-built fixture scenarios; local compilation alone would not do so. Native install/rotation/recovery producer acceptance, managed endpoints, other desktop storage, collector enrollment/acknowledgments and broad user/admin/async coverage remain required. No readiness gate is promoted.

## Edit profiles in a recorded desktop session

On Linux amd64/arm64, an unelevated operator can open a dedicated profile-editing session against a locally enrolled stream from the same actor/build/target:

```text
accessweaver audit ui --directory /home/operator/.accessweaver-profile-audit --from trusted-genesis.json --to trusted-head.json > new-checkpoint-observations.jsonl
```

Initialize a new private stream and retain its genesis independently first, using audit initialize as described above. Startup information and the OS-private browser launcher location use stderr; stdout contains only canonical checkpoint lines. Keep these destinations separate and private. Direct regular-file aliases of either checkpoint input, the journal or actor key refuse for both stdout and stderr. Direct regular-file stdout/stderr aliases also refuse. Shell truncation occurs before the command starts; always choose new destinations, and ensure any wrappers or downstream pipes do not forward output into protected inputs or combine startup text with checkpoint JSONL.

This session permits profile listing, creation, editing, deletion, JSON import through the editor's save route, and read-only launch previews. Each actual save/delete dispatch records profile.write/profile.delete intent before invoking the store, with a fresh operation ID, then a synchronous completed/refused/canceled/indeterminate result before returning API success. Browser JSON imports use profile.write because the HTTP operation is the same reviewed save. The session disables engine launches/stops, workflows, diagnostics and support export in the interface and refuses their API routes. It seeds no built-in profiles. Invalid request/session, malformed body, active-profile checks and other pre-dispatch route refusals are not recorded; this is operation coverage rather than a complete access/attempt log. Preview responses and per-profile JSON downloads do not create audit events.

Existing loopback, token/origin checks, sixteen-request admission bound, serialized active-profile checks, controller ownership, profile locks, revision compare-and-save/delete and managed permissions still apply. The journal is opened and verified before profile-store creation. Opening creates directory/lock metadata only; it never seeds or saves profiles outside the recorder. A recorder reserves room for both records before dispatch and requires the complete durable intent checkpoint to reach its observation output. A failed/short intent output prevents dispatch and attempts a local refusal; no more writes use that broken output channel. The session then refuses subsequent mutations. A failed result append/output or indeterminate operation also disables further mutations until independent reconciliation; there is no automatic retry, rollback, replacement stream, rotation or destructive recovery.

Known successful store commits remain completed even if a request disconnects immediately afterward. Result recording uses a separate cooperative fifteen-second context after cancellation. Unknown filesystem/cancellation races and panics report indeterminate without raw error/panic text. A fully recorded refusal can preserve its ordinary policy/revision error to the API caller; error details are never placed in audit records. The observation stream is not a collector acknowledgment or durable external checkpoint retention. Retain each full checkpoint through a trusted channel, including those from refused operations; preserve ambiguous journal tails independently. Do not mistake two checkpoint lines or the observation stream for a single checkpoint input.

The recorder serializes complete transactions and holds the source writer lock for the session. On shutdown it waits for any active callback/result write before closing storage and releasing controller ownership. Native filesystem/stdout I/O can block beyond the HTTP/read/result context budgets; no hard termination or power-loss durability claim is made. At full capacity the session continues to permit reads/previews and refuses mutations. Close the session before read-only audit export, which conflicts with its exclusive source lock. Other builds require separately enrolled streams; upgrading this primitive does not implement cross-stream continuity.

Protected signed policy can require recorded application profile changes with requireProfileAudit plus allowProfileChanges. Ordinary UI/CLI writes/deletes and bulk backup restores then refuse without an active action-matched recorder context; built-in seeding skips its writes. The explicit audit import and audit ui paths carry a revocable context only during their synchronous operation, after the durable intent checkpoint reaches output. A write/import context cannot delete, a delete context cannot save, and the context is inactive after the callback, including panic. The store still rechecks managed permission under its lock. See [managed profile-audit restrictions](MANAGED_CONFIGURATION.md) for deployment, compatibility and direct-filesystem limitations. This is scoped application profile enforcement, not mandatory auditing of engine/workflow/admin/read/export activity or authentication of a human requester. Other desktop storage, collector transport/acknowledgments/retention, mandatory export-access coverage, packaged endpoint and full native acceptance remain open. The enterprise audit gate remains missing.

## Export a verified segment with explicit consent

Linux amd64/arm64 can export the local journal's canonical event records directly to a JSONL file or an existing trusted log-agent pipe. Every invocation must include the exact consent value metadata-only. Missing, repeated, unknown or different consent/options refuse before input is read. The output contains actor/source linkage, event times, operation IDs and action/outcome metadata; treat it as security-sensitive even though profile contents and raw principal/key/error values are excluded.

```text
accessweaver audit export --directory /home/operator/.accessweaver-import-audit --from trusted-genesis.json --to trusted-head.json --consent metadata-only > new-events.jsonl
accessweaver audit verify --events new-events.jsonl --from trusted-genesis.json --to trusted-head.json
```

Use a new output destination. Export requires the independently authenticated complete genesis and exact retained head, verifies the entire bounded stream before emitting bytes, and excludes the journal's first genesis line. Its output is the canonical event JSONL accepted by audit verify, with no status wrapper or added fields. Existing collectors can parse those records with their JSON-line input and the separately enrolled producer/checkpoint association. No collector address, credentials, network client, transport authentication, ingestion test or durable acknowledgment is configured by this command.

The source is opened read-only and held under a shared nonblocking OS lock, which refuses a cooperating active writer. The same protected-directory ancestry, owner/private mode, local persistent filesystem, single-link and stable-file checks apply. Source handles close before stdout writes; the export describes the requested retained endpoint, not freshness after that snapshot. Extra/partial/lost records, stale endpoints, cancellation or changed bindings produce no success prefix. A later stdout failure can leave partial destination output; it must still pass exact ending-checkpoint verification before use.

Historical archives can be exported after a build change or loss of the private actor key: the key is unnecessary for verification and no key content is read or recreated. For direct regular-file stdout, a metadata-only O_PATH identity probe helps refuse output that aliases the actor key or source journal; the CLI also refuses direct aliases of either checkpoint input. Arbitrary writer wrappers or downstream pipes must not forward data back into those inputs. Shell redirection can truncate a file before the program starts, so the command cannot repair damage from choosing an existing input as the destination. No append, sync, deletion, key creation, profile operation or automatic repair is performed by the snapshot reader.

The read/verification context is cooperative and uses a 15-second budget; native filesystem and stdout calls are not subject to a hard whole-command deadline. Export never infers/authenticates an endpoint from disk, enrolls a new actor, acknowledges collection or advances retention. It does not append an audit.export event to a historical source. The separate [export-recorded command](RECORDED_AUDIT_EXPORT.md) adds current-stream access intent/outcome with a separate observation stream; it does not change this archive command. Authenticated enrollment and managed export enforcement, collector transport/acknowledgment, retention, other desktop backends and packaged endpoint acceptance remain required before enterprise audit qualification.

## Canonical version-one format

Every checkpoint and event record is one canonical UTF-8 JSON object followed by exactly one LF byte. Field order and scalar encodings match the checked-in vectors. Duplicate, unknown, case-aliased or missing fields, null substitutions, alternate number encodings, invalid UTF-8, CRLF, extra whitespace, partial final records and trailing data refuse.

A checkpoint contains schemaVersion, streamID, producer, sequence and sha256. Stream IDs are random 128-bit values encoded as 32 lowercase hexadecimal characters. Sequences are integers from zero through 2^53 minus one for exact JSON collector interoperability. Sequence zero must match its computed genesis hash.

Producer fields are actorClass (user or administrator), actorSHA256, sourceCommit, sourceState and target. The actor hash is a wire claim; the verifier performs no OS identity lookup. The separate internal ProcessProducer factory described below derives execution-principal metadata for local recording and future controller/administrator producers. Source commits are complete 40/64-character lowercase hexadecimal IDs or explicit unknown; an unknown commit requires unknown source state. Targets retain all ten documented Windows/Linux/macOS/FreeBSD/OpenBSD amd64/arm64 combinations. A producer change requires another stream and separately trusted enrollment.

Each record contains schemaVersion, streamID, sequence, previousSHA256, producerSHA256, event and sha256. Its producer digest binds producer metadata even when verification starts at a nonzero checkpoint. The event contains only:

| Field | Contract |
| --- | --- |
| occurredAt | Nonzero UTC timestamp, canonical RFC3339 with optional fractional seconds; the producer's clock claim |
| operationID | 128-bit correlation ID encoded as 32 lowercase hexadecimal characters |
| action | One of the fixed actions below |
| outcome | intent, accepted, completed, refused, failed, canceled or indeterminate |

Actions are profile.write, profile.delete, profile.import, engine.start, engine.stop, workflow.submit, workflow.cancel, workflow.complete, policy.install, policy.update, policy.rotate, policy.remove, policy.recover, backup.create, backup.restore, support.export and audit.export. Accepted work and completed work have distinct outcomes. The format does not infer that an action occurred or reconcile intent/result pairs.

There is no free-text, path, URL, request-body, error, token, profile-name or command-line field. Future producers must construct hashes and correlation IDs from the intended sources; placing a secret in a field shaped like a digest would still disclose that secret. The verifier checks the format and checkpoint linkage rather than sanitizing deliberately misconstructed producer metadata.

A segment requires one stream/producer, strictly consecutive sequences, exact predecessor hashes and the expected final checkpoint. It is capped at 4,096 records and 2,048 bytes per record. Verification retains one record at a time and returns no partial result on cancellation, transport error, excess data, malformed input or endpoint mismatch. Clock rollback is retained as a clock claim; sequence establishes record order.

## Hash construction and interoperability

The digest primitive is Go's [SHA-256 implementation of FIPS 180-4](https://pkg.go.dev/crypto/sha256). Domain separation uses the bytes AccessWeaver audit v1 followed by NUL, then the label below and another NUL:

| Label | Hashed canonical JSON bytes, without LF |
| --- | --- |
| producer | The producer object |
| genesis | An object containing streamID followed by producer |
| record | The record fields in their defined order, excluding the final sha256 field |

The JSONL fixtures under internal/audit/testdata were computed independently using Python hashlib and explicit ordered JSON. Their producer, source and action are synthetic test values. The golden genesis is f46a1fa94779261f1f1af27a88fe00ce2bdb37d8b5ea4249371ffd39eec170d4; the one-record head is 583c916334fd758f8f5dbc020654193591b86955da324d96d35cb4f2b216887f.

```text
accessweaver audit verify --events internal/audit/testdata/events.jsonl --from internal/audit/testdata/genesis.json --to internal/audit/testdata/end.json
```

Run this repository example from a source checkout. It checks format interoperability. Its self-contained synthetic checkpoints are not evidence of a deployed audit trail.

## Native execution-principal metadata

The internal ProcessProducer factory reads the executing OS principal and buildinfo.Current source metadata for all ten documented targets. It performs no account-name, directory-service, environment-identity or network lookup, creates no stream, and writes no event. A caller must supply a dedicated random 32-byte actor pseudonymization key, protect it separately from exported checkpoints, and authenticate its enrollment independently. The factory rejects an all-zero key; that check does not establish entropy or protect a caller-chosen weak key. Do not reuse signing, policy, enrollment-authentication or other secrets for this purpose.

The actorSHA256 field contains HMAC-SHA-256 over the domain bytes AccessWeaver audit v1, NUL, process-actor, NUL, OS name, NUL, principal scheme, NUL and the canonical native principal string. The scheme is uid for Unix and sid for Windows. The raw UID/SID and key are excluded from producer output and error messages. This pseudonym is stable only within its keyed OS namespace; it is not a signature or proof of enrollment. A low-entropy UID can be guessed if its pseudonymization key is disclosed. Key scope must distinguish installations, UID namespaces and enrollment lifecycles; UID reuse cannot identify a new human account without administrative reenrollment. The independent synthetic Linux UID-1000 vector with key bytes 00..1f is 6b3b544e27dc61c7a86ceac6517162669292d0f2279061ba9f1b59f690fdb512.

Unix reads real/effective UID and GID twice and refuses mixed or changing credentials. The executing effective UID is the principal; administrator means UID zero, with every other UID classified as user. This does not evaluate supplementary groups, capabilities or application roles. Windows reads the process token's SID and elevation status while pinned to one OS thread, and refuses a thread impersonation token or any token-query error. It changes no token or context. [OpenThreadToken](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-openthreadtoken) supplies the impersonation-context check; [TOKEN_ELEVATION](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-token_elevation) defines zero/nonzero elevation classification.

These are execution-principal observations. They do not identify an HTTP requester, a person who earlier elevated the process, a login name or a human. OS credentials must not change concurrently with recording. Live producers must reconstruct and compare this metadata before each operation, retain OS/requester attribution separately if required, and enroll another stream for changed principal/class/source/target/key metadata. Parsing a producer supplied by someone else still authenticates none of these claims. Source fields are build-reported provenance, not publisher verification. This factory grants no policy authority. The explicit Linux audit import caller records events using its metadata; the explicit audited desktop records profile saves/deletes; broader controller integration remains unfinished.

Portable tests independently check the HMAC vector, key/principal/OS separation, all ten target encodings, explicit unknown or malformed source handling, fixed private errors and resistance to spoofed identity environment variables. Native Unix tests check actual effective credentials and pure mixed/changed-credential refusals. A separately opted-in disposable hosted Windows fixture duplicates only its own token, requires impersonation to refuse, then verifies exact identity restoration. No account, policy, privilege or installed-product change is part of that fixture. Its actual Windows acceptance and full collector-backed attributable auditing remain separate requirements.

## Linux journal storage component

The internal Linux amd64/arm64 journal stores one genesis checkpoint and up to 4,096 canonical event records in events.journal, bounded by 1,024 bytes plus 8 MiB. The explicit audit initialize/import CLI uses this storage, with read-only snapshots exposed by audit export. The explicit audited desktop connects profile-save/delete producers, explicit policy commands connect install/update/rotation/recovery, and export-recorded connects access intent/outcome for a current-stream snapshot. Other controller producers remain unconnected. The existing audit verify command still reads exported JSONL; the journal includes its genesis line and is not itself that export format.

A trusted caller must supply an already opened directory with protected ancestor bindings, effective-UID ownership and mode 0700 on persistent ext4, XFS or Btrfs storage. The component borrows that handle, retains its own descriptor, and exclusively creates or opens a private mode-0600, single-link file relative to it. Existing content/permissions are never repaired. Symlinks, extra hard links, changed file identity, unexpected ownership/modes, nonpersistent storage and excessive input refuse. Root and same-UID processes remain within the storage trust boundary; local hashes do not authenticate them.

The writer holds a nonblocking exclusive OS lock for its lifetime and serializes threads. It validates the complete existing stream against its retained head before each append. Initialization syncs both the genesis file and containing directory. Append reports a new checkpoint only after an exact write, file fsync and a final file/entry check. Cancellation is checked before mutation; once a write starts, its actual durability outcome is reported even if the context is canceled. Filesystem calls, mutex acquisition and fsync do not have a deadline supplied by this API. The single-operation CLI checks two-record capacity before dispatch; future controller/background producers must also supply bounded admission and explicit required-audit behavior.

A failed/short write or failed sync returns no checkpoint, makes that handle unavailable for further append/snapshot, and preserves every existing byte. Such an error does not prove a record is absent. Reopening requires the independently retained complete genesis and expected ending checkpoint. Partial data, an extra complete record or missing records refuse. The implementation never infers a trusted new head from an unknown tail, truncates it, starts a replacement stream, retries an uncertain append or removes the journal. An administrator must reconcile uncertain state independently; an explicitly reconciled complete endpoint is verified and synced before reopening succeeds. Keeping the checkpoints beside the journal would not create an independent trust channel.

Snapshot returns a bounded copy with both endpoints after full verification. It grants no export consent or collector acknowledgment. At capacity the journal refuses new events. Rotation, deletion, acknowledgment persistence and retention are deliberately unavailable until the collector protocol can authorize them.

Linux race tests cover real storage/reopen, concurrent writers, stale endpoints, alias/mode/content replacement, full capacity, injected ENOSPC/partial writes/sync errors, cancellation and volatile-filesystem refusal. Two source-built subprocess fixtures are killed after actual half/complete writes before fsync; both preserve prior and unacknowledged bytes, and reopening with the old endpoint refuses. These process interruptions are not reboot or power-loss tests. Use a private persistent native directory for TMPDIR when running the journal tests; WSL's memory-backed /tmp is correctly refused. Native hosted Linux amd64/arm64 runs, hardware durability and the other desktop storage implementations remain separate acceptance requirements.

## Remaining implementation and acceptance

The pure Append function prepares one record and its successor checkpoint. It performs no I/O; the Linux journal supplies one storage implementation. A live durable producer must commit the record before advancing a saved head and preserve ambiguous interrupted writes for reconciliation. It must enforce protected ownership/ACLs, bounded admission and storage, retention tied to collector acknowledgment, independently pinned checkpoints and accurate asynchronous outcomes. Required-audit failures must have explicit behavior before operations are dispatched; a result-write failure after an operation cannot be treated as proof that the operation did not occur.

Controller/CLI/privileged-helper coverage, enrollment of OS-derived actor attribution, managed consent/export-access coverage, collector deployment and hostile-input/crash/full-disk/native acceptance across the supported desktop matrix remain required. [NIST SP 800-92](https://csrc.nist.gov/pubs/sp/800/92/final) provides the enterprise log-management context for those operational requirements. This protocol and CLI add no readiness score credit.


The [0e22324 native Linux required-profile-audit acceptance](qualification/0e2232468942-linux-required-profile-audit.json) passed on hosted amd64 and arm64 using source-built disposable fixtures. The reports and complete original report bytes are source-bound and their provider ZIP digests were verified. This establishes that scenario on those two hosted targets; signed installed-product/managed-endpoint behavior, broad administrative/async action coverage, collectors and the full enterprise audit gate remain incomplete.

The [separate hosted recorded-policy fixture](LINUX_RECORDED_POLICY_ACCEPTANCE.md) defines full CLI/native install, update, rotation and damaged-source recovery coverage with exact source preservation on refusals and a sixteen-record metadata export. Local compilation does not establish those new native cases; exact hosted results remain pending.
