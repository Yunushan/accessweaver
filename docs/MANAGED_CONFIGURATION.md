# Signed managed configuration

Current status: signed administrator documents and partial Windows, Linux and macOS runtime enforcement through protected machine configuration. The production/enterprise readiness gates remain partial. Verification alone returns `runtimeEnforced: false`; offline tools do not enroll or authorize a machine. Windows initial installation and monotonic updates use native registry transactions. BSD machine policy, complete unreadable-storage recovery, independent revision escrow, protected input staging, service authorization and managed-endpoint qualification remain work.

## Document and trust contract

A policy contains `schemaVersion: 1`, a monotonically increasing `revision`, `issuedAt`, `expiresAt`, permission booleans (`allowDiagnostics`, `allowProfileChanges`, `allowDownloads`), the optional `requireProfileAudit` restriction, launch/workflow approvals and optional pinned `downloads` rules. An empty allowlist and false permissions express denial. The verifier checks the supplied clock, rejects expiry at or before that clock, and allows issuance at most five minutes ahead for clock skew. Revisions must be positive JSON-safe integers (at most 9007199254740991). Changing any policy byte, including whitespace, invalidates its signature.

The optional signed `allowWorkflowHistoryRetirement` permission defaults to false when absent and is separate from profile changes, profile audit and workflow approvals. It prepares an identity- and expiry-bound authorization check for a future explicitly reviewed local history-retirement operation; it does not enable a retirement endpoint, native workflow action or record deletion in this version. Invalid or unavailable machine policy never becomes unmanaged authorization, and a changed policy invalidates a retained grant even when the replacement also permits retirement. False is omitted when encoding policy, preserving existing signed payload bytes; older strict readers reject policies containing the new field rather than ignoring it. No recovery-evidence eligibility rule or deployment-readiness claim follows from this permission.

The separate signed `allowWorkflowLifecycleReconciliation` permission also defaults to false when absent. It governs explicitly reviewed local lifecycle metadata reconciliation: preview and apply acquire fresh grants bound to the current policy identity and expiry, with a final check before returning authorization. A changed, revoked, expired or unavailable policy cannot reuse a retained grant or become unmanaged permission. Profile, workflow and history-retirement grants cannot substitute for this permission, and it grants no deletion, retirement, native or vendor action. It does not prove release of unknown owners; reconciliation still requires the supported positive ownership evidence. Receipt and status inspection retain their ordinary authenticated history permissions. False is omitted when encoding policy, preserving existing payload bytes; prior strict readers reject a document containing this new field rather than silently ignoring it.

The envelope has four fields: `schemaVersion`, `keyId`, `payload` and `signature`. `payload` is standard padded base64 of the exact UTF-8 policy bytes. `keyId` is lowercase SHA-256 of the raw 32-byte Ed25519 public key. `signature` is standard padded base64 of an Ed25519 signature over the bytes `AccessWeaver managed policy v1` followed by a NUL byte and then the exact payload. Trust keys require canonical compressed coordinates and reject every small-order point before signature verification. Curve decoding and signatures still use the Go standard library. This avoids treating a degenerate-key signature equation as proof of a signing secret. Coordinate encoding follows [RFC 8032](https://www.rfc-editor.org/rfc/rfc8032#section-5.1.3); the low-order coordinate set is cross-checked against the [tagged libsodium reference](https://github.com/jedisct1/libsodium/blob/1.0.20-RELEASE/src/libsodium/crypto_core/ed25519/ref10/ed25519_ref10.c). No algorithm negotiation or envelope-supplied public key is accepted. The verifier uses only the public key selected independently by the operator. The implementation uses [Go's Ed25519 package](https://pkg.go.dev/crypto/ed25519).

Policy input is limited to 64 KiB, envelopes to 128 KiB, and each launch/workflow/download allowlist to 128 rules. Unknown fields, case aliases, duplicate keys at any level, trailing documents, noncanonical base64, malformed hashes and inconsistent private keys are rejected. Use UTF-8 without a BOM for signed policy documents. The original payload remains embedded in the envelope; decoding and re-encoding it before verification is invalid.

`--minimum-revision N` requires a policy revision strictly greater than N. N must come from trusted prior deployment state. The review command does not save it, enroll a key, rotate trust, import policy, prevent local state rollback or change profiles. Windows runtime verifies the revision floor in the protected installation value. `managed update` derives the next floor from the authenticated enrolled revision; direct administrator/MDM registry writes must preserve that invariant themselves. Passing a command-line number alone is not persistent rollback protection.

## Require recorded profile changes

A protected signed policy may set `"allowProfileChanges": true` together with `"requireProfileAudit": true`. The optional restriction defaults to false when absent, preserving existing policy behavior. Its exact boolean value is covered by the policy signature and revision/expiry checks. Null, nonboolean, duplicate and case-aliased fields refuse before signing/verification. Older clients that do not understand this field refuse the policy rather than silently dropping it.

When enabled, the application's revision-checked profile save/delete paths require an active, action-matched in-process audit intent. The recorder persists the intent and writes its complete checkpoint observation before supplying this context to the synchronous callback; it revokes the context before recording the result. A saved context cannot authorize another operation afterward, a write/import intent cannot delete, and a delete intent cannot save. HTTP fields/headers, environment values and caller-selected context keys cannot construct this capability. The policy is checked again under the profile lock before mutation, so an active intent grants no exception to revoked profile permission or unavailable machine policy.

The explicit `audit import` and `audit ui` producers supply this context; see [audit setup and checkpoints](AUDIT_EVENTS.md). Ordinary UI/CLI imports, unrecorded store writes/deletes and backup snapshot restoration refuse profile mutations while this restriction applies. Built-in seeding skips its writes and completion marker. Profile reads remain available. Bulk restore has no connected audit producer and cannot reuse a single-profile intent. Directory/lock metadata may still be created when a store opens; the restriction covers profile content publication/deletion, not every filesystem access.

Initialize and independently enroll a private stream for the intended operator/build/target before enabling the restriction. Recording has native backends for Linux, Windows and macOS on amd64/arm64. Windows uses the [private local NTFS source candidate](WINDOWS_AUDIT_STORAGE.md), whose real CLI/managed acceptance remains pending. macOS uses the [protected native APFS backend](DARWIN_AUDIT_STORAGE.md); that guide distinguishes source-built hosted command acceptance from the remaining installed-endpoint and durability requirements. BSD machine-policy enforcement remains unsupported; the portable verifier cannot activate this restriction on BSD. Missing/full/uncertain storage or failed intent output prevents dispatch. A post-mutation audit failure remains uncertain and requires independent reconciliation, with no automatic retry or destructive reset.

This flag governs application profile mutations. It does not require audit for engine/workflow/admin actions, exports or reads; authenticate a collector/producer; enforce durable acknowledgments/retention; or protect profile files from direct writes by their OS owner or an administrator. The in-process producer and native policy/storage code remain trusted, and callbacks must not fork or reuse an intent for unrelated operations. Endpoint permissions and administrative controls must address direct filesystem access separately. Full enterprise audit and native managed-endpoint qualification remain incomplete; no readiness gate is promoted by the restriction.

The source-built disposable Linux acceptance fixture includes an ordinary-user CLI roundtrip against the real enrolled fixed machine-policy source. It retains the original denial/revocation/corruption cases and a separate fifteen-second worker budget. The [0e22324 native Linux evidence](qualification/0e2232468942-linux-required-profile-audit.json) verifies that this scenario passed on hosted amd64 and arm64, including both source-bound policy reports and provider ZIP digests. Local compilation alone would not establish that result. Collector enrollment, broad action coverage, packaged endpoint behavior and other target qualification remain separate.

## Offline administrator workflow

Keep signing keys outside the source checkout and managed endpoints, on a protected signing workstation. Only unencrypted Ed25519 PKCS#8 PEM input is currently supported; HSM, encrypted-key and signing-service integration remain work. This utility does not generate or change key-file permissions. An existing organization key may be used, or [OpenSSL `genpkey`](https://docs.openssl.org/3.5/man1/openssl-genpkey/) can create an offline Ed25519 key:

```bash
umask 077
openssl genpkey -algorithm ED25519 -out signer.private.pem
accessweaver managed public-key --private-key signer.private.pem
```

Transfer only the printed public key to the review/deployment environment through your trusted administrative channel. The output is base64 of the raw public key, not a PEM block or base64 of an entire SubjectPublicKeyInfo document. Never distribute the private signing key with the envelope, logs or support artifacts.

Author a policy with current UTC validity timestamps. This example expresses denial of all governed operations when deployed as protected Windows installation data. The signing command alone does not activate it:

```json
{
  "schemaVersion": 1,
  "revision": 1,
  "issuedAt": "2026-11-01T00:00:00Z",
  "expiresAt": "2026-11-02T00:00:00Z",
  "allowDownloads": false,
  "allowDiagnostics": false,
  "allowProfileChanges": false,
  "launches": [],
  "workflows": []
}
```

Set actual issuance/expiry values before signing, then run:

```bash
accessweaver managed validate policy.json
accessweaver managed sign policy.json --private-key signer.private.pem --out envelope.json
accessweaver managed verify envelope.json --public-key BASE64_PUBLIC_KEY --minimum-revision 0
```

`--out` writes UTF-8 directly and exclusively creates a new output file. An existing file is never overwritten, including when it names the signing key or policy source. A write, sync or close failure returns an error; any incomplete new file is retained for inspection and must not be distributed. Without `--out`, signing writes to stdout; PowerShell 5.1 redirection encodes stdout as UTF-16, so use `--out` there. To create the source policy from PowerShell 5.1, use `[IO.File]::WriteAllText(path, json, [Text.UTF8Encoding]::new($false))` rather than its BOM-producing UTF8 `Set-Content`.

Review output includes the parsed policy, key ID, payload SHA-256, `signatureValid: true`, and `runtimeEnforced: false`. Invalid input returns a nonzero exit status with no successful review JSON. None of these commands starts an engine, probes a network, writes application profile state, changes Windows settings or installs policy.

## Binding approvals to inputs

```bash
accessweaver managed digest-profile profile.json
accessweaver managed digest-workflow request.json
```

These commands print `inputSHA256` and `runtimeEnforced: false`. A digest grants no authority by itself. It must match an approval in the signed, protected machine policy.

A launch input digest binds version, engine, binary/configuration references, the profile's expected executable hash, arguments and all routing lists. Display identity, names, descriptions, notes, update timestamps and diagnostic probes are excluded because they do not control engine launch. Empty and absent lists normalize consistently; the profile SHA-256 spelling normalizes to lowercase. Other list ordering and spelling remain significant. Separate `binarySHA256` and optional `configSHA256` rule fields are required to identify file contents rather than only their references. Approval must also cover executable dependencies and referenced assets through future provenance checks.

A workflow digest binds every field of the validated typed `workflow.Request`, including its action, engine, paths, selected applications, domain/target lists, flags, URL/hash and journal ID. JSON formatting and omitted zero values normalize through that typed representation. Unknown actions receive no digest. Input digests use SHA-256 of `AccessWeaver managed launch input v1` or `AccessWeaver managed workflow input v1`, followed by a NUL byte and the respective typed JSON bytes. CLI and runtime use the same helpers. Compatibility vectors retain the version-one digests produced by commit `0178f99`.

Launch rules contain `engine`, `inputSHA256`, `binarySHA256` and optional `configSHA256`. Workflow rules contain `action` and `inputSHA256`. Duplicate engine/action plus input-hash approvals are rejected. The supported runtime backends compare these approvals before execution and checks permission again at mutation/start boundaries. Separate input-provenance limits below still apply. Installation data is user-readable approval data, so manifest URLs must not carry credentials or private tokens.

## Protected Windows source and runtime behavior

Windows reads only the 64-bit registry view at `HKLM\SOFTWARE\Policies\AccessWeaver`, value `Installation` of type `REG_BINARY`. The installation is a UTF-8 JSON object containing `schemaVersion`, `publicKey`, `minimumRevision` and the signed `envelope`. Current native publication uses storage version two with its mandatory acceptance companion; version one remains a legacy format. [Accepted local history](MACHINE_POLICY_ACCEPTANCE.md) describes that distinction. One value prevents readers mixing a new key, old revision floor and different envelope. The key and fixed ancestors must be owned by SYSTEM, Administrators or TrustedInstaller, with no ordinary-principal rights to mutate values, subkeys, ownership or DACLs. Ordinary deny ACEs, inherit-only ACEs and Windows owner placeholders are handled explicitly; unsupported ACE forms fail closed. [Windows documents registry access rights](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-key-security-and-access-rights).

An absent protected key means unmanaged. A present key with a missing/empty value, weak ACL, inaccessible data, invalid signature, stale revision or expired policy blocks governed actions; it never silently falls back to unmanaged mode. `ACCESSWEAVER_HOME`, user profiles, browser storage and environment variables cannot choose the authority. There is no user-facing bypass switch.

Prepare a candidate file locally with the existing pinned public key and trusted prior revision:

```bash
accessweaver managed prepare envelope.json --public-key BASE64_PUBLIC_KEY --minimum-revision 0 --out installation.json
accessweaver managed status
```

Preparation validates the envelope and exclusively creates a UTF-8 file. It does not write the registry. Existing endpoint-management tooling can invoke the separately elevated `managed install` command below, rather than modifying an adopted enrollment directly. Manual version-one `REG_BINARY` deployment remains a legacy compatibility path without paired history; new native writes publish the installation and acceptance record together, with administrator-only mutation and ordinary-user reads. A suitable leaf descriptor is `O:BAG:BAD:P(A;;KA;;;SY)(A;;KA;;;BA)(A;;KR;;;BU)`. Validate deployment only on disposable managed test endpoints first. No test in the ordinary unit suite creates, modifies or deletes HKLM keys on its host.

`managed status` reports `supported`, `configured`, `valid`, `storageVersion`, authenticated `acceptedRevision` when present, the enrolled `keyId`, revision/expiry and `enforcement` (`none`, `partial` or `blocked`). Invalid/unreadable state returns a nonzero exit status and structured blocked status; configured includes state that cannot safely be excluded because source protection failed. Linux amd64/arm64 use the protected file source described below. macOS amd64/arm64 use the fixed paired APFS source described in [macOS policy](MACOS_MANAGED_POLICY.md); BSD targets still report unsupported machine enforcement. Offline `managed verify` still reports `runtimeEnforced: false` because a reviewed file is not machine enrollment.

Current guarded paths are:

- Profile save, revision-based save, delete and first-run seeding. Read-only policy skips seeding. Saves/deletes check permission again after acquiring the storage lock; reads remain available.
- CLI and authenticated API diagnostics before probing a network.
- Foreground launch preview, preparation and final process start. Approval binds the version-one input digest and expected binary/configuration hashes. Generated routing files and raw native-argument assets fail closed until protected staging/validation exists. Files require trusted administrator ownership and non-user-writable ancestor/sibling protection on fixed local drives. Reparse points and alternate data streams are refused; directory inspection is streamed and bounded to 4096 entries/32 levels, and individual hashing to 512 MiB. This conservatively excludes locations such as ordinary user directories and default broadly writable ProgramData ancestors. Use qualified immutable application storage; native location/alias compatibility remains to be tested.
- Reviewed Windows workflow requests, rechecked after preview and again by the actual worker. Supplied configuration/bundle paths must pass native provenance checks. Managed Visual C++ runtime and Windows Packet Filter setup use the approved bundle or a policy-pinned download. The implicit SplitWire prerequisite directory is available only for unmanaged setup. Raw native-argument assets and auto-install (which generates native arguments from scan output) are blocked pending protected compilation and authorization. Approved standalone scans remain available, but executable provenance is not yet qualified: discovery can use implicit component or SplitWire locations outside the approved bundle path. `allowDownloads: false` blocks release lookups and component retrieval before network activity. With downloads enabled, `downloads` entries pin each implicit dependency's exact HTTPS URL and SHA-256; remote release metadata cannot replace a pin. A directly approved `download` request already binds its own URL/hash through the signed request digest. Publisher verification remains an additional check for signed installers. Network activity intrinsic to an approved vendor program, including explicitly approved WARP registration, still needs vendor/native qualification.
- The `service-host` entry point. Enrolled machines currently reject these service starts until signed service-specific authorization and protected broker integration exist. Existing running jobs/services are not automatically revoked or terminated by policy changes. Pending starts cannot outlive manager shutdown while waiting for policy/provenance I/O.

Native workers resolve system tools through `GetSystemDirectoryW`. Shared storage is derived from the ACL-checked machine `ProfileList\ProgramData` setting, expanding only OS-derived SystemDrive/SystemRoot/WINDIR values. Program Files and common-program roots likewise come from protected machine registration rather than caller environment values. This avoids caller-environment expansion in the ordinary common-directory API. Tests compare the result with that API in the normal environment and repeat lookup in a fresh process with poisoned environment values. PowerShell workers use a trusted working directory and module path, remove CLR/module/runtime injection variables, and use protected temporary storage for machine changes. Managed foreground engines receive a sanitized environment tied to the same authority read as final launch authorization. These controls do not sandbox an approved vendor executable.

## Initial installation and monotonic updates

Run these commands through the existing endpoint-management channel or a separately elevated administrator/root CLI. Keep the dashboard unelevated. They change the fixed machine policy source and require an effective administrator token, including when the calling thread impersonates a user.

```bash
accessweaver managed install installation.json --public-key BASE64_PUBLIC_KEY
accessweaver managed update next-envelope.json
accessweaver managed status
```

`install` requires the public key obtained independently through the administrator's trusted channel and checks it against the prepared document. It refuses every existing policy key, including damaged or expired installations, rather than replacing enrolled trust. New keys have administrator-only mutation/ownership permissions and ordinary-user read access. No user-selected registry path is accepted.

`update` accepts only an envelope. It reads the enrolled key and authenticates the previously accepted policy, requires a strictly higher revision signed by that same key, and saves that previous revision as the new floor. It never accepts a replacement key or caller-supplied floor. Identical and older revisions are errors; competing imports of the same revision cannot both commit. The updater reserves the native value for writing and compares it with the separately read committed document before deriving approval, so a stale reader must abort after another revision commits. Invalid signatures, damaged prior state and unknown source protection stop the update. There is no automatic bootstrap or reset fallback.

An expired prior policy remains blocked for runtime operations. The updater can authenticate its original signature and recover its revision at its issuance time solely to validate a fresh, currently valid higher revision. This historical check does not construct runtime authority or reuse expired permissions. A missing, corrupted or unauthenticatable prior policy needs a separately reviewed administrator recovery procedure; this command does not bypass it.

On Windows, the implementation uses a local [KTM transaction](https://learn.microsoft.com/en-us/windows/win32/api/ktmw32/nf-ktmw32-createtransaction) and [transacted registry handles](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regopenkeytransactedw), with a 15-second transaction timeout and no named coordination object. Initial key creation and both `Installation` and `Acceptance` values are staged before one commit. Reads and writers retain pair consistency and stale-preimage checks. Version-two native storage requires its companion record; existing version-one storage is migrated on its next successful native change. See [protected acceptance state](MACHINE_POLICY_ACCEPTANCE.md) for the format, migration and counter trust limits. Pending state is not published; closing the last uncommitted transaction handle aborts it. Candidate validity is checked again after staging, so expiry during contention prevents commit. There is no non-transactional fallback if the native facility is unavailable. The transaction DLL is loaded from the OS system directory, independent of application/current directories and PATH.

Successful output contains the operation, previous/new revisions, key ID, payload hash, `committed: true` and `enforcement: "partial"`. It excludes signing keys and policy contents. A transaction conflict or failure returns nonzero; inspect `managed status` before retrying. Console/handle failures can occur after commit, so a failed invocation must not be treated as proof that no change took effect. Never restore an older installation document to make a retry pass. Keep reviewed policy sources offline; to reverse policy intent, sign the desired settings again with a new revision. Publisher signing, last-known-good recovery, power-loss/reboot acceptance and integration with real endpoint-management deployment remain unfinished.

## Planned signing-key rotation

Windows, Linux and macOS support a separately elevated `managed rotate` command. It uses the same platform-specific protected storage transaction, stale-state check, final expiry check and complete installation document as ordinary updates. The old key authorizes one exact replacement key and signed policy; the replacement policy's signature proves possession of the new key. The accepted revision must still increase. Rotation does not reset the floor or bootstrap a missing/damaged source.

Export the current public installation document on an enrolled endpoint, then transfer it through the administrative channel to the offline signing environment:

```bash
accessweaver managed export-installation --out previous-installation.json
```

Export checks native source protection and authenticates its historical signature/revision. It can export an expired policy for renewal/rotation planning without authorizing its permissions. It contains the public key and public approval data; keep its access appropriate to the organization. It contains no private signing key. Output uses exclusive creation and never overwrites an existing file. Machine export on BSD remains unsupported.

Author a currently valid next policy with a revision higher than the enrolled revision and sign it with the new key. Obtain `NEW_PUBLIC_KEY` from that key and `OLD_PUBLIC_KEY` through the independent trusted channel. On the offline signer, run:

```bash
accessweaver managed sign next-policy.json --private-key next.private.pem --out next-envelope.json
accessweaver managed sign-rotation next-envelope.json --previous-installation previous-installation.json --next-public-key NEW_PUBLIC_KEY --private-key old.private.pem --out rotation.json
accessweaver managed verify-rotation rotation.json --previous-installation previous-installation.json --public-key OLD_PUBLIC_KEY
```

The old private key must match the authenticated prior installation. The new key must differ, and the next envelope must have a valid new-key signature, validity window and higher revision before signing. The review command independently pins the old public key and reports previous key/revision/payload hash, the next verified policy and `runtimeEnforced: false`. Signing and review do not install, probe a network, or create application user state. Never transfer either private key to an endpoint.

Deploy only the public rotation document through the existing management channel and apply it in the separately elevated CLI:

```bash
accessweaver managed rotate rotation.json
accessweaver managed status
```

The endpoint binds authorization to its actual enrolled key ID, revision and exact signed policy payload SHA-256. Any intervening policy update, even to different contents at the same revision through an administrator's direct write, makes the old rotation stale. Export and sign against the current state again. After commit, ordinary updates signed by the retired key are rejected; updates require the new key. Replaying the rotation is rejected. The result includes previous/new key IDs and revisions with `committed: true` and `enforcement: "partial"`.

The rotation wrapper uses the same four-field envelope encoding but a separate signature domain: UTF-8 `AccessWeaver managed key rotation v1`, a NUL byte, then the exact payload bytes. The payload contains `schemaVersion: 1`, `previousKeyId`, `previousRevision`, `previousPayloadSHA256`, `nextPublicKey` and `nextEnvelope`. The old key signs the complete payload. The embedded new policy retains its own ordinary policy signature and exact payload bytes. Unknown/duplicate/case-aliased fields, noncanonical base64, mismatched prior state and invalid signatures are rejected. Rotation payloads are bounded to 132 KiB and outer envelopes to 192 KiB; ordinary policy/envelope limits still apply. Rotation signatures cannot authorize ordinary policy documents or vice versa.

An expired prior policy can participate in planned rotation through historical metadata authentication, while runtime operations remain blocked until a currently valid replacement commits. Expiry of the replacement prevents signing/review/apply. This is planned rotation with possession of the old key. Loss or compromise of that key, corruption of the trust source, out-of-band recovery, protected last-known-good state and fleet rollout/reboot qualification remain separate requirements. A holder of the old private key can authorize transitions while that key remains enrolled; this procedure does not solve signer compromise. Keep the old key offline and retire it according to the organization's signing controls after qualified rollout.

## Protected Linux source and update behavior

Linux amd64/arm64 reads the fixed `/etc/accessweaver/installation.json` and its protected `acceptance.json` companion. Native writers use a version-two installation wrapper containing the reviewed key, minimum revision and signed envelope; portable preparation remains version one. Legacy installations without acceptance remain partially enforced until a successful native change adopts the pair. User roots, profiles, environment variables and the working directory never select this authority. Every path component must be a real root-owned directory without group/other write or set-ID permissions. Both policy files must be root-owned, regular, singly linked, bounded and non-user-writable; symlinks, FIFOs and devices are refused. Descriptor-relative opens and `O_NOFOLLOW` keep lookup anchored to checked directories; an `O_PATH` inspection rejects special files before opening them for reading. An absent protected directory means unmanaged. A present directory with missing, inaccessible, malformed, expired or weakly protected data blocks governed operations.

The source parent, directory and file require qualified persistent local filesystem semantics: the ext family, XFS or Btrfs. Volatile, layered, remote, FUSE and unknown source filesystems fail closed pending qualification. Root ownership and non-writable group/other bits also exclude effective named-user/group POSIX ACL writes because the group bits represent the ACL mask. [Linux documents this mask correspondence](https://man7.org/linux/man-pages/man5/acl.5.html). These checks do not establish disk, mount, hardware or power-loss qualification across all installations.

Use the same `managed prepare`, `install`, `update`, `export-installation`, `sign-rotation`, `verify-rotation` and `rotate` commands. Machine writes require a separately elevated root CLI; keep the dashboard under the desktop user. Initial installation independently pins the supplied public key, stages a complete directory privately, syncs its contents and publishes it with `renameat2(RENAME_NOREPLACE)`. It refuses any existing destination, including an empty/damaged directory, and has no weaker fallback when that facility is unavailable. Newly created product objects have inherited POSIX ACL entries removed before their explicit modes are applied, so inherited named-user denials do not make the public policy unreadable. Readers never alter existing ACLs. The resulting directory is mode 0755 and public installation file mode 0644, both owned by root.

All product writers coordinate through the persistent root-owned mode-0600 `/etc/.accessweaver-policy.lock` file. Ordinary users cannot open it to take a writer lock. Lock contention is bounded to 15 seconds; readers remain lock-free and see a complete old or new policy. Product code never deletes the coordination inode, including after failed bootstrap. Administrators and deployment tools must not delete or replace it while writers may exist. Direct writes outside this protocol can invalidate state and are not a supported concurrent update method.

Updates and rotation retain the protected current key/revision rules. They write and sync a complete two-file sibling generation, check both retained preimages and the active directory identity/layout, atomically exchange directories with `RENAME_EXCHANGE`, and sync the parent. Unknown active contents cause refusal before exchange. Readers use one directory descriptor and bounded retries across publication. Cleanup retains independently changed displaced contents. A failed operation may have reached publication before a later sync/close failure, so inspect `managed status` before retrying; never restore an older revision as an automatic fallback. Full reboot/power-loss and real endpoint-management recovery remain acceptance requirements.

The staging namespace `/etc/.accessweaver-policy-stage-<32 lowercase hex characters>` is reserved for paired generations. Legacy `/etc/.accessweaver-install-<32 lowercase hex characters>` and `/etc/accessweaver/.installation-<32 lowercase hex characters>` candidates are also reclaimed when safe. Under the same persistent writer lock, the next operation reclaims abandoned candidates after checking their ownership, type, link count, permissions, size and expected contents. Scans are streamed and limited to 4096 directory entries and 128 candidates per operation. Unexpected files, symlinks or oversized data are preserved and produce an inspection error. Do not put unrelated administrator files into these reserved namespaces. This cleanup does not recover a corrupted or deleted enrolled trust source or signing key.

Current profile/diagnostic/foreground guards consume this Linux authority. Approved foreground inputs must use canonical absolute paths with root-owned, non-writable ancestors and a protected dedicated engine directory. The directory walk rejects symbolic/hard links and unsafe adjacent objects, streams at most 4096 entries/32 levels, and caps individual hashing at 512 MiB. Executable input files require ELF format; interpreter scripts/assets, raw native arguments and generated routing files remain blocked until qualified protected compilation exists. Configuration contents still require their signed hash. Use immutable deployment storage; general system executable directories often contain links and are not automatically suitable bundles.

Managed Linux children receive only fixed `PATH=/usr/bin:/bin`, `LANG=C`, `LC_ALL=C` and `TZ=UTC`, with no caller-selected home/configuration, loader, shell or runtime variables. Vendor executables still require dependency/configuration qualification and OS deployment controls; this is not a sandbox against arbitrary same-user code or execution in a different OS namespace. Native routing, services and privilege-separated operations remain separate requirements.

For explicit intent/outcome recording of Linux install, update, key rotation and signed recovery, use the [recorded policy transaction commands](AUDIT_EVENTS.md#record-an-explicit-policy-transaction). They wrap these same native operations without changing privilege or trust. Ordinary managed commands and endpoint-management writes are not automatically audited; a native error may follow publication and remains uncertain. Keep the administrator journal outside the fixed policy directory, retain checkpoints independently, and inspect state before any retry. Broad mandatory audit and collector integration remain incomplete.

## Disposable hosted Linux acceptance

The [33c7737 source-built hosted results](qualification/33c7737d97cd-linux-recorded-policy-audit.json) verify the explicit administrator policy-update producer and its two-record consented export on Linux amd64/arm64, followed by the existing independent UID/GID 65534 required-profile-audit roundtrip. Other administrative producers, packaged endpoints and collector-backed deployment remain separate acceptance requirements.

`test-linux-managed-policy.sh` compiles static test executables as the ordinary runner user, then invokes only the scoped native cases with sudo on a fresh GitHub-hosted Linux runner. It requires `ACCESSWEAVER_DISPOSABLE_LINUX_POLICY_TEST=1`, the hosted Linux context and absence of existing policy/coordination state. Never enable that flag on a workstation or self-hosted runner. Ordinary unit tests use private temporary directories and read-only source inspection; they do not install `/etc` policy.

The test creates only its owned policy/coordination state and an inert ELF fixture under a unique `/etc/accessweaver-policy-test-...` directory. A child with UID/GID 65534 and no supplementary groups must read policy, fail policy/binary writes and profile changes, reject unauthorized update/rotation, and start only the approved fixture with the fixed environment. A real named-user ACL grants write but masks it off for the positive case; enabling that mask write must block authority. Tests also reject tampered executable bytes, writable policy directories and invalid installed JSON.

A separate process-exit test abandons initial/update/rotation stages, verifies that they never publish authority, confirms lock release and candidate reclamation, then checks key rotation, retired-key/replay denial and new-key updates. Cleanup checks the exact allocated directory/inode before deleting test state; only the disposable tests remove their newly created coordination file after all their writers exit. Public source-bound records are retained in `build/managed-policy-checks/linux-native-policy.json` and `linux-policy-transactions.json`. No vendor software is installed and no routing, DNS, firewall or network probes are applied. Hosted native checks are configured for amd64 and arm64; inspect their separate source-bound records. They do not qualify other distributions/filesystems, desktop/MDM behavior, reboot or physical power loss.

## Policy changes during active operations

Foreground engines, workflow workers and network diagnostics retain the authenticated key ID, exact signed payload hash and expiry used at their final authorization check. Before starting, then once per second, a monitor reads the fixed protected native source again. It also schedules a check at the retained expiry when sooner. Any payload/key change, enrollment of a previously unmanaged machine, removal of an enrolled source, expiry or source/verification failure cancels the operation. Even a newer policy with identical permissions requires explicit review and restart. Source recovery does not resurrect a canceled job. Plan maintenance windows for policy updates; do not rotate or refresh policy over active production work without accounting for this interruption.

Engine cancellation terminates the owned foreground process (the process group on Unix) and records a policy error. Workflow cancellation uses the existing worker cancellation path; a worker that returns success after observed policy cancellation is recorded as failed, with the policy reason preserved in history. Status/shutdown locks are not held during monitor source I/O. Monitors are released when their operation exits. These checks do not repeatedly hash unchanged engine bundles or authorize new inputs.

The one-second polling interval is not a hard real-time bound: scheduling, native source I/O and process termination can take longer, and a transient change between checks can be missed. Revocation does not undo completed changes, stop independently installed services/tasks or prove restoration of routing, DNS or vendor state. Ordinary cancellation/recovery journals and separate administrator recovery still apply; there is no automatic rollback under a policy that may forbid it. Active diagnostics close their owned TCP/UDP sockets on observed policy cancellation and return a policy error (HTTP 403 or a nonzero CLI status). Service-host authorization remains a separate gap. Physical reboot/power-loss, desktop/MDM rollout and vendor cleanup qualification remain required.

Disposable hosted acceptance checks an actual native update while an engine runs, including a Linux ordinary-user controller with UID/GID 65534. It also checks that an unsafe Linux source ACL and an invalid Windows source terminate active fixtures. Portable tests cover enrollment, inaccessible sources, expiry timers, terminal cancellation, restart and durable workflow failure when a worker returns a success result after cancellation. These tests use inert foreground children and do not qualify vendor network recovery.

## Remaining integration and acceptance

[Signed administrator recovery](MACHINE_POLICY_RECOVERY.md) now handles existing bounded, readable protected sources with exact-state approvals and independent key/revision pins. [Protected local accepted history](MACHINE_POLICY_ACCEPTANCE.md) now detects primary-only rollback and raises the signed-recovery floor with an intact companion. Automatic last-known-good fallback, independent revision escrow and unsafe/unreadable native-storage recovery remain outstanding; transactional install/update and planned key rotation need full desktop, reboot and deployment qualification; manual endpoint-management writes can misconfigure state, and a trusted administrator can replace it. Complete BSD authority storage/enforcement and native Windows/Linux/macOS deployment qualification, protected generated/native-argument inputs, signed service authorization and privilege separation. Test supported Windows versions/architectures, relocated/native path aliases, dependency/configuration behavior, full expiry/revocation and vendor recovery while jobs run, reboot, upgrade/downgrade and uninstall recovery. Policy can deliberately block recovery or uninstall requests too, so deployment must include a separately reviewed administrator recovery procedure. Do not deploy an empty allowlist over active production services as an experiment.

All controllers and service copies must use the qualified build. Publisher signing and OS application-control/deployment rules are still needed to prevent older or modified binaries, arbitrary same-user code injection and execution outside this installation from bypassing an application-level check. The current implementation is not an isolation boundary against arbitrary code with the controller's permissions.

Tests cover signatures and strict parsing, revision/time boundaries, native descriptor validation, read-only registry access, approval/provenance decisions, profile-lock and workflow/start revocation races, API denial, pinned download contracts and a real read-only PowerShell discovery process under an untrusted environment. Native install/routing/managed-domain acceptance remains a disposable-VM qualification requirement. No compilation, mocked provenance decision or ordinary CI pass grants full enterprise readiness credit.

## Disposable hosted Windows acceptance

The dedicated CI/release step runs `TestDisposableManagedPolicyNative` and `TestDisposablePolicyTransactionRollback` on a fresh GitHub-hosted Windows VM after ordinary tests. It requires the explicit `ACCESSWEAVER_DISPOSABLE_POLICY_TEST=1` opt-in, the hosted Windows runner context, an administrative non-SYSTEM account and absence of any existing AccessWeaver policy. Never set this flag on a desktop or self-hosted runner. [GitHub documents per-job hosted VM isolation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job).

The tests temporarily create a protected policy key through the actual installer and one uniquely named protected Program Files fixture directory. It approves and starts an inert test-only executable, checks read-only profiles and denied diagnostics/workflows/service starts, probes registry/file write denial with an impersonated token whose administrator SID and privileges are disabled, rejects changed executable bytes and verifies that invalid installed policy cannot become unmanaged. Cleanup removes only its newly created key and validates the exact fixture directory before recursive deletion. It does not install vendor software, change services/DNS/firewall settings or send network probes. The fixture branch exists only in a Go test binary and is absent from production builds. Additional checks cover actual initial installation, refusal to replace an enrolled key, concurrent same-revision updates, signing-key substitution and expired-policy renewal. A second test stages initial/update documents without commit, reads the previously committed state, then closes or abruptly exits a child process and requires native rollback before a later valid update. A deterministic stale-reader case also attempts reservation after a newer revision has committed and requires rejection without changing that revision. Rotation checks abruptly exit a child with a staged new key, require the old key/revision to remain effective, then commit the rotation, reject replay/retired-key updates and accept a new-key update. These tests create persistent registry keys only for the duration of the disposable job and delete their own keys during cleanup; they do not qualify reboot/power-loss behavior.

Public result metadata is retained under `build/managed-policy-checks/`; check the exact source-bound CI run for its outcome. Separate hosted Windows Server amd64 and Windows 11 ARM64 jobs exercise the native core/policy checks. Their records do not qualify all Windows versions, domain/MDM enrollment, interactive browser behavior or real driver/network lifecycle acceptance. Failed cleanup fails the test; an evidence field indicating scheduled cleanup alone does not prove completion.

## Protected macOS source and update behavior

macOS amd64/arm64 use the fixed root-owned local-APFS source `/Library/Preferences/AccessWeaver/{installation.json,acceptance.json}`. Root-only CLI enrollment, update, rotation and signed recovery publish the pair atomically under a private writer lock. A companion acceptance record is mandatory even when a version-one offline preparation exists. Unsafe or inconsistent state blocks governed operations. [The macOS implementation and native acceptance procedure](MACOS_MANAGED_POLICY.md) define ACL checks, full-sync ordering, bounded Mach-O/bundle input inspection, sanitized child environment and remaining signing, crash/recovery and endpoint-deployment limits. Inspect both architectures' exact-source disposable acceptance results before treating a candidate as natively qualified.

The [managed auto-install guard regression](qualification/fc5a23e295b5-managed-auto-install-guard.json) passed in four Windows/Linux native unit reports and both Linux race reports. It covers signed approval denial before workflow storage, unmanaged auto-install and approved managed standalone scan. Managed auto-install remains unavailable until its generated native assets have protected staging and authorization. The same source’s ARM64 DNS wire observation was refused after a TCP reset; this does not establish the absence of plaintext traffic.
