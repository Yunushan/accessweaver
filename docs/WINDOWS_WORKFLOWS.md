# Windows installation and repair

The **Installation & repair** dashboard and `system` CLI manage Windows components separately from foreground profiles. They require Windows PowerShell 5.1. The dashboard must run as the normal desktop user. Its administrative handoff is unfinished, so applying machine changes currently requires a separately elevated `system apply` CLI invocation. Application install, removal and start must run unelevated in the intended desktop account. Inspection and preview work without elevation. See the verification limits in [SECURITY.md](../SECURITY.md) before deployment.

These workflows are experimental. See [implementation and verification status](SPLITWIRE_IMPLEMENTATION.md) before deployment. Native results apply to the recorded Windows build and component versions, not every network or vendor release.

## Review and run

Select an operation and component, then review the generated plan. Machine plans identify their administrator requirement and remain unavailable to apply from the unelevated dashboard. **Export reviewed request** downloads only the reviewed JSON request, without a session token, plan ID or approval. Keep the file private: native arguments and paths may be sensitive. Review it again with `system preview` and explicitly apply it in a separately elevated CLI. Eligible user operations can be confirmed and applied in the dashboard. Changing an input invalidates the plan. Plans expire after ten minutes and can be consumed once. Controllers and CLI processes using this version allow one accepted operation at a time per data directory. A competing start is refused before native execution; review the current operation before trying again. Machine operations also use an administrator-only mutex across data directories; user application operations take a separate Windows mutex scoped to the current account across data directories and desktop sessions. Install, remove, reinstall and start refuse while another AccessWeaver application operation holds it. The mutex coordinates cooperating controllers. Vendor tools, older controllers and other Windows accounts have independent operation paths. Inspect retained journals and the desktop before retrying an interrupted operation.

The CLI accepts the same JSON request:

```powershell
accessweaver.exe system operations
accessweaver.exe system discover
accessweaver.exe system presets
accessweaver.exe system preview request.json
accessweaver.exe system apply request.json --confirm
accessweaver.exe system history
```

`system history` and the final `system apply`/`system discover` snapshot use compact JSON with a trailing newline. Their fields, complete result values and full retained legacy errors are preserved; metadata strings stream in bounded chunks. Redirect exports to a private file; they can contain configuration, paths and tool output. An output-write failure returns an error and can leave an incomplete destination file. Dashboard report reads preserve complete result values with compact streaming JSON. A busy status reader receives HTTP 503; the dashboard retries that read without repeating the reviewed operation. Cancellation and history use separate admission, and interrupted report transfers are aborted rather than completed as partial downloads.

Pressing Ctrl+C during `system apply` requests cancellation and begins an eight-second diagnostic wait. If the worker has not finished, the CLI shows fixed waiting feedback and keeps owning the job until execution and its final status write attempt return. It then prints the actual final snapshot and returns a nonzero exit status. The diagnostic timeout does not become a terminal job state or permit the command to abandon its worker. A blocked native operation or status write can therefore keep the command active indefinitely. Inspect the recovery journal before retrying. A vendor cleanup or rollback is not certified by the controller merely exiting.

For example, install an automatic ByeDPI proxy service without app interception:

```json
{"action":"install","engine":"byedpi","mode":"service","dns":"unchanged"}
```

ByeDPI listens on `127.0.0.1:1080`. Applications must use this proxy, or select `split` mode to install ProxiFyre and its Windows Packet Filter prerequisite. `dll` mode deploys drover to an installed stable Discord. `once` runs until cancellation. Optional `applications` and `browsers` compile the interception selection; default selections include Discord and Roblox.

## Packet engines and hostlists

Zapret, Zapret2 and GoodbyeDPI support `install` with `mode: "service"` or `"once"`. Choose an included preset or supply `args` as a JSON string array. Every argument is passed literally, without a shell. Zapret2 needs matching Lua assets. System installation owns its hostlist arguments; use the foreground profile runner for independently managed native list options.

Use `hostlist` with `domains` and `enabled` to save or toggle the list. Zapret/Zapret2 lists are exclusions; GoodbyeDPI lists are inclusions. Disabling preserves the saved list. GoodbyeDPI restarts to update its blacklist argument. Zapret reload behavior depends on the upstream version. A service/list test does not establish filtering effectiveness.

`scan` and `auto-install` run upstream blockcheck with `scan: "quick"`, `"standard"` or `"full"`. Provide its Windows bundle, including Cygwin, through `bundlePath`. `targets` are the hosts to test; `domains` are unrelated hostlist entries. Zapret2 tries the included ISP strategies before its broader scan. Full mode maps to upstream's force scan.

Auto-install selects only a completed reported common strategy, preferring HTTPS. It refuses incomplete output, shell commands and incompatible native strategies. Reports are retained. A scan for HTTPS is not a UDP voice or ISP reliability test.

## DNS and application maintenance

DNS configuration first reads the complete DNS-client inventory. An Up adapter with no exposed client family is not targeted. Originals are captured separately for IPv4/IPv6; reconfiguration adds a newly exposed family before changes while preserving earlier originals and global DoH metadata. Recovery preflights and restores only captured families. New `bound4`/`bound6` snapshot fields describe this coverage, and legacy snapshots retain their both-family recovery contract. Invalid coverage, unreadable state or a missing owned family retain the snapshot and refuse further changes.

Static link-local IPv6 originals are saved without a volatile interface zone. ## Ownership, cancellation and recovery

[History inspection](WORKFLOW_HISTORY.md) describes the explicit private inventory, bounded pages and exact selected-record exports. The existing complete history export remains available; this browser does not retire recovery evidence.

Before publishing a native worker result, the worker checks the complete UTF-8 JSON byte count against 32 MiB. It writes a fresh sibling staging file, flushes and closes it, then promotes it only if the result filename is absent. Write, flush, close and promotion failures retain uncertain staging and cannot overwrite an existing result. Every newly executed report carries a version and a fresh launch token; the controller rejects stale or mismatched output. This token provides correlation, not authentication of user-writable storage or publisher identity. Legacy history remains readable.

An oversized, unencodable or over-depth result produces a small failed-report envelope when storage permits. It omits the large data/events, retains bounded recovery-journal and reboot context, and is reported as a result failure even if the operation had already changed system state. Reporting failure does not rerun the operation or establish rollback. The byte check bounds result-file writes; serialization and the source object graph are not claimed to have a hard memory bound. Whole-store quotas and reviewed retirement remain separate work. The explicit history inventory provides bounded paging while retaining recovery evidence.

Worker finalization independently attempts the recovery-journal save, owned machine mutex release and disposal, then bounded result publication. Earlier failures do not skip later cleanup or publication. The result retains at most four unique `finalizationFailures` codes: `journal-save`, `mutex-release`, `mutex-dispose` and `uninstaller-start`. The controller preserves journal-save failure as persistence uncertainty and the other codes as cleanup uncertainty, alongside execution or reporting failures. Publication failure remains a failed operation and preserves uncertain staging.

The controller's uninstall action checks for an incomplete Setup before restoring DNS or removing managed resources. It holds the installer lifecycle mutex during that cleanup and checks the pending installation record again before deferred handoff. A deferred product uninstaller is skipped if journal or mutex cleanup fails. An eligible handoff is marked `externalEffectsPending` before launch, and the protected journal is not rewritten after releasing the mutex. Non-read-only native tools and desktop application handoffs also retain uncertainty about external effects. This flag alone is not execution failure or proof that an external operation completed. `recordedRollbackComplete` applies only to `rollbackScope: "recorded-resources"`; when native effects remain pending, a successful recorded rollback uses `recovery-attempted` rather than certifying complete vendor rollback. Neither result nor journal state authorizes retirement.

The data directory retains `.workflow-active.lock` and `.workflow-store.lock` beside the `workflows` directory. These are OS-owned coordination files, not PID files: leave them in place, including after a crash. The active lease covers admission, execution, output draining and the final record-write attempt. Record writes also take a short store transaction lock. Status and cancellation remain available during storage waits. A reported lock-close failure remains in the live terminal outcome and prevents further admission by that Manager. The terminal record was written before active-lease release, so that record alone does not certify a successful release or authorize later retirement. Read-only history does not create these files or initialize a missing directory. Older versions and external programs do not participate in this protocol; different data directories have independent leases. This is coordination for cooperating processes, not a machine-wide user-operation mutex, storage quota or authorization to retire recovery evidence.

Local release acknowledgments now require observed closure of the original controller owners, including the actual process wait, output-pipe drains, record writer and active lease. A canceled branch that never called the native executor is tracked explicitly. Successful callback returns, a failed job record and currently free locks do not establish that proof. When a known closed acknowledgment stage needs recovery, the separate [reviewed local reconciliation](WORKFLOW_HISTORY.md#reviewed-local-reconciliation) can preserve that exact stage and retry the acknowledgment after fresh review and permission checks. The original failed outcome stays unchanged; unknown crash owners remain protected.
