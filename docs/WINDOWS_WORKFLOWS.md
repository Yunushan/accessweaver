# Windows installation and repair

The **Installation & repair** dashboard and `system` CLI manage Windows components separately from foreground profiles. They require Windows PowerShell 5.1. The dashboard must run as the normal desktop user. Its administrative handoff is unfinished, so applying machine changes currently requires a separately elevated `system apply` CLI invocation. Application install, removal and start must run unelevated in the intended desktop account. Inspection and preview work without elevation. See the verification limits in [SECURITY.md](../SECURITY.md) before deployment.

These workflows are experimental. See [implementation and verification status](SPLITWIRE_IMPLEMENTATION.md) before deployment. Native results apply to the recorded Windows build and component versions, not every network or vendor release.

## Review and run

Select an operation and component, then review the generated plan. Machine plans identify their administrator requirement and remain unavailable to apply from the unelevated dashboard. **Export reviewed request** downloads only the reviewed JSON request, without a session token, plan ID or approval. Keep the file private: native arguments and paths may be sensitive. Review it again with `system preview` and explicitly apply it in a separately elevated CLI. Eligible user operations can be confirmed and applied in the dashboard. Changing an input invalidates the plan. Plans expire after ten minutes and can be consumed once. Controllers and CLI processes using this version allow one accepted operation at a time per data directory. A competing start is refused before native execution; review the current operation before trying again. Machine operations also use an administrator-only mutex across data directories; user application operations do not share that machine mutex.

The CLI accepts the same JSON request:

```powershell
accessweaver.exe system operations
accessweaver.exe system discover
accessweaver.exe system presets
accessweaver.exe system preview request.json
accessweaver.exe system apply request.json --confirm
accessweaver.exe system history
```

`system history` and the final `system apply`/`system discover` snapshot use compact JSON with a trailing newline. Their fields, complete result values and full retained legacy errors are preserved; metadata strings stream in bounded chunks. Redirect exports to a private file; they can contain configuration, paths and tool output. An output-write failure returns an error and can leave an incomplete destination file. Dashboard report reads preserve complete result values with compact streaming JSON. A busy status reader receives HTTP 503; the dashboard retries that read without repeating the reviewed operation. Cancellation and history use separate admission, and interrupted report transfers are aborted rather than completed as partial downloads.

Pressing Ctrl+C during `system apply` requests cancellation and begins an eight-second diagnostic wait. If the worker has not finished, the CLI shows fixed waiting feedback and keeps owning the job until execution and its final status write attempt return. It then prints the actual final snapshot and returns a nonzero exit status. The diagnostic timeout does not become a terminal job state or permit the command to abandon its worker. A blocked native operation or status write can therefore keep the command active indefinitely. Inspect the recovery journal before retrying. A vendor cleanup or rollback is not certified by the controller merely exiting.

For example, install an automatic ByeDPI proxy service without app interception:

```json
{"action":"install","engine":"byedpi","mode":"service","dns":"unchanged"}
```

ByeDPI listens on `127.0.0.1:1080`. Applications must use this proxy, or select `split` mode to install ProxiFyre and its Windows Packet Filter prerequisite. `dll` mode deploys drover to an installed stable Discord. `once` runs until cancellation. Optional `applications` and `browsers` compile the interception selection; default selections include Discord and Roblox.

Unsigned assets require a SHA-256 digest; signed vendor installers also require successful Authenticode verification. Downloads and dependencies remain governed by their own licenses. A hash identifies an artifact; it does not establish its trustworthiness. ## WireSock

`install` with `engine: "wiresock"` supports `alternative` (WireSock only), `standard` (WireSock plus ByeDPI/drover) and `custom` (selected apps). `config` generates only a private configuration. `connect`, `disconnect`, `refresh` and `remove` manage its lifecycle. Explicit `disconnect` retires the scheduled reconnect task before disconnecting and keeps the managed profile and ownership record for removal. Use `remove` before importing a profile again. Modern Secure Connect uses its vendor CLI, and the legacy SDK client retains its own service commands. If the WireSock installer requests a Windows restart, setup stops before starting services or importing a profile. Restart Windows before retrying setup.

Supply `configPath` to avoid registering an account. A new wgcf/WARP account requires explicitly setting `acceptCloudflareTerms: true` after reviewing [Cloudflare's terms](https://www.cloudflare.com/application/terms/). ## Packet engines and hostlists

Zapret, Zapret2 and GoodbyeDPI support `install` with `mode: "service"` or `"once"`. Choose an included preset or supply `args` as a JSON string array. Every argument is passed literally, without a shell. Zapret2 needs matching Lua assets. System installation owns its hostlist arguments; use the foreground profile runner for independently managed native list options.

Use `hostlist` with `domains` and `enabled` to save or toggle the list. Zapret/Zapret2 lists are exclusions; GoodbyeDPI lists are inclusions. Disabling preserves the saved list. GoodbyeDPI restarts to update its blacklist argument. Zapret reload behavior depends on the upstream version. A service/list test does not establish filtering effectiveness.

`scan` and `auto-install` run upstream blockcheck with `scan: "quick"`, `"standard"` or `"full"`. Provide its Windows bundle, including Cygwin, through `bundlePath`. `targets` are the hosts to test; `domains` are unrelated hostlist entries. Zapret2 tries the included ISP strategies before its broader scan. Full mode maps to upstream's force scan.

Auto-install selects only a completed reported common strategy, preferring HTTPS. It refuses incomplete output, shell commands and incompatible native strategies. Reports are retained. A scan for HTTPS is not a UDP voice or ISP reliability test.

## DNS and application maintenance

DNS configuration first reads the complete DNS-client inventory. An Up adapter with no exposed client family is not targeted. Originals are captured separately for IPv4/IPv6; reconfiguration adds a newly exposed family before changes while preserving earlier originals and global DoH metadata. Recovery preflights and restores only captured families. New `bound4`/`bound6` snapshot fields describe this coverage, and legacy snapshots retain their both-family recovery contract. Invalid coverage, unreadable state or a missing owned family retain the snapshot and refuse further changes.

Static link-local IPv6 originals are saved without a volatile interface zone. Restoration resolves the saved adapter GUID again before each family write and supplies zone-free canonical values to that current IPv6 CIM row. The row selects the interface; setter strings do not carry a volatile scope suffix. Legacy numeric zones must match the saved original index; malformed or ambiguous static addresses retain the snapshot and are rejected before DNS or DoH changes. A newly exposed family uses the live adapter index during capture while preserving earlier originals. DHCP families continue to restore by resetting their owned family.

The [family-coverage qualification](qualification/e86aa1c10cde-dns-family-coverage.json) includes successful actual DoH configuration, ordinary-resolver queries and original-state restoration on fresh hosted Windows AMD64/ARM64. The separate oracle verifies dormant registry state for non-exposed families without calling them DHCP. This does not qualify DNSCrypt, encrypted wire transport, failure/reboot recovery or the full DNS gate.

## Ownership, cancellation and recovery

[History inspection](WORKFLOW_HISTORY.md) describes the explicit private inventory, bounded pages and exact selected-record exports. The existing complete history export remains available; this browser does not retire recovery evidence.

Before publishing a native worker result, the worker checks the complete UTF-8 JSON byte count against 32 MiB. It writes a fresh sibling staging file, flushes and closes it, then promotes it only if the result filename is absent. Write, flush, close and promotion failures retain uncertain staging and cannot overwrite an existing result. Every newly executed report carries a version and a fresh launch token; the controller rejects stale or mismatched output. This token provides correlation, not authentication of user-writable storage or publisher identity. Legacy history remains readable.

An oversized, unencodable or over-depth result produces a small failed-report envelope when storage permits. It omits the large data/events, retains bounded recovery-journal and reboot context, and is reported as a result failure even if the operation had already changed system state. Reporting failure does not rerun the operation or establish rollback. The byte check bounds result-file writes; serialization and the source object graph are not claimed to have a hard memory bound. Whole-store quotas and reviewed retirement remain separate work. The explicit history inventory provides bounded paging while retaining recovery evidence.

Worker finalization independently attempts the recovery-journal save, owned machine mutex release and disposal, then bounded result publication. Earlier failures do not skip later cleanup or publication. The result retains at most four unique `finalizationFailures` codes: `journal-save`, `mutex-release`, `mutex-dispose` and `uninstaller-start`. The controller preserves journal-save failure as persistence uncertainty and the other codes as cleanup uncertainty, alongside execution or reporting failures. Publication failure remains a failed operation and preserves uncertain staging.

A deferred product uninstaller is skipped if journal or mutex cleanup fails. An eligible handoff is marked `externalEffectsPending` before launch, and the protected journal is not rewritten after releasing the mutex. Non-read-only native tools and desktop application handoffs also retain uncertainty about external effects. This flag alone is not execution failure or proof that an external operation completed. `recordedRollbackComplete` applies only to `rollbackScope: "recorded-resources"`; when native effects remain pending, a successful recorded rollback uses `recovery-attempted` rather than certifying complete vendor rollback. Neither result nor journal state authorizes retirement.

The data directory retains `.workflow-active.lock` and `.workflow-store.lock` beside the `workflows` directory. These are OS-owned coordination files, not PID files: leave them in place, including after a crash. The active lease covers admission, execution, output draining and the final record-write attempt. Record writes also take a short store transaction lock. Status and cancellation remain available during storage waits. A reported lock-close failure remains in the live terminal outcome and prevents further admission by that Manager. The terminal record was written before active-lease release, so that record alone does not certify a successful release or authorize later retirement. Read-only history does not create these files or initialize a missing directory. Older versions and external programs do not participate in this protocol; different data directories have independent leases. This is coordination for cooperating processes, not a machine-wide user-operation mutex, storage quota or authorization to retire recovery evidence.

Local release acknowledgments now require observed closure of the original controller owners, including the actual process wait, output-pipe drains, record writer and active lease. A canceled branch that never called the native executor is tracked explicitly. Successful callback returns, a failed job record and currently free locks do not establish that proof. When a known closed acknowledgment stage needs recovery, the separate [reviewed local reconciliation](WORKFLOW_HISTORY.md#reviewed-local-reconciliation) can preserve that exact stage and retry the acknowledgment after fresh review and permission checks. The original failed outcome stays unchanged; unknown crash owners remain protected.

The CI workflow offers a manual `workflow-store` scope for native Linux, Windows and macOS file-lock fixtures on both architectures. It runs the source-owned file-lock and workflow-store tests without installers or vendor actions. Normal push, pull-request and manual `full` runs retain the complete CI jobs. This focused scope does not qualify ordinary-user deployment, installed products or complete desktop behavior.

Desktop shutdown closes workflow admission alongside engine shutdown and retains the controller until the exact reserved workflow completes, including admission and final status persistence. The eight-second workflow wait controls a diagnostic notice; a background join continues until actual completion. Current workflow failures are returned through the desktop shutdown result with fixed admission/execution/result/persistence/cleanup/store labels. Private underlying causes remain available to local code without being copied from the display error or printed unbounded on stderr. A failed final status save remains failure even if the tool itself exited successfully. See [engine and desktop lifetime](ENGINE_LIFETIME.md) for ownership limits.

Components, private profiles, service configuration, backups and persistent logs live under `%ProgramData%\AccessWeaver`, with administrator/SYSTEM access. Foreground profiles and workflow history use the ordinary AccessWeaver data directory. New history records retain compact result JSON (up to 32 MiB); the summary error is capped at 16 KiB with a visible truncation notice. Inspect the full result, when available, and private process log for details. Legacy full-history listing has a combined 64 MiB read limit; old records and recovery evidence are not automatically deleted or repaired. Keep private configurations and logs out of public issue reports. The dashboard shortens large/deep result previews and marks them visibly. Use **Export latest status** for the current controller report or **Export full history** for complete retained JSON. These private exports can contain sensitive configuration or tool output and are separate from the metadata-only support summary. Downloads do not delete or modify history.

`remove` removes a selected managed method; `remove-all` removes owned methods in dependency order and restores DNS/drover files. Independent services, vendor installations and private recovery evidence are retained. Explicit WinDivert removal verifies that the driver's path belongs to the managed component store; shared external drivers are refused.

The Windows installer registers a normal uninstaller. It restores owned system changes before deleting the application and aborts deletion when restoration fails. Portable users can run `uninstall`, stop the core, then remove the portable directory. Protected recovery data is retained for review.

Cancellation requests termination of the owned worker tree. Before the consuming child wait, the controller reserves that exact process identity with a verified, noninherited duplicate handle. Cancellation waits for binding, and the reservation remains held through helper completion and actual child wait/output drain. A binding failure refuses numeric tree dispatch, retains cleanup uncertainty and still waits the accepted child; the controller never reopens the worker by numeric ID. The service host likewise retains stop-pending status and its log while cleanup or the actual wait remains unresolved. A helper failure leaves descendant cleanup unconfirmed even if the parent exits; that failure is retained separately from the process exit status. Sudden termination can bypass PowerShell cleanup, so inspect the journal before retrying. The recovery action accepts only a protected journal filename:

```json
{"action":"recover","journalId":"workflow-0123456789abcdef0123456789abcdef.json"}
```

Recovery validates resource ownership and expected file hashes. It refuses to overwrite files changed independently since installation. DNS changes and imported managed WireSock profiles have explicit recovery entries. Vendor installers can make changes outside the journal; restore the disposable VM checkpoint when validating them.

## Building and testing

The unsigned installer is built with an explicitly supplied Inno Setup compiler and a Windows Go SDK matching the intended core payload:

```powershell
./scripts/build-windows-installer.ps1 -Compiler 'C:\Tools\Inno Setup\ISCC.exe' -Version 0.1.0 -TargetArch amd64
# On an ARM64 Windows build host with its ARM64 Go SDK:
./scripts/build-windows-installer.ps1 -Compiler 'C:\Tools\Inno Setup\ISCC.exe' -Version 0.1.0 -TargetArch arm64
```

`-TargetArch` defaults to the Go SDK host architecture and rejects cross-host builds because the staged core must execute its `version --json` check. The build checks its PE machine before execution, then compares version, source commit/state, build time, compiler, platform and architecture. Outputs are named `accessweaver-VERSION-windows-amd64-setup.exe` or `accessweaver-VERSION-windows-arm64-setup.exe`. The corresponding [Inno architecture requirement](https://jrsoftware.org/is6help/topic_setup_architecturesallowed.htm) is `x64compatible` or `arm64`, with 64-bit install mode for each. Inno Setup 6 retains its x86 bootstrap; an ARM64 payload does not imply a native ARM64 setup runtime, vendor drivers, signing or installation qualification. The existing application ID is shared; cross-architecture upgrades still require disposable-VM testing.

`scripts/test-windows-workflow.ps1` runs filesystem/pure-function contracts and mocked DNS cmdlets without changing host services or networking. `scripts/test-windows-integration.ps1` deliberately changes a disposable guest; it checks for a virtual machine and an administrator token. It requires a test-only binary/component bundle and writable results directory. Run it only in an explicitly disposable guest, never a production VM.

`scripts/build-windows-fixtures.ps1` builds the optional WireGuard userspace peer and selected/unselected traffic probes from separately pinned modules. ## Administrator machine policy

A protected signed Windows policy can restrict workflow requests and remote component retrieval, independently of the caller's user data root. Requests must match their signed input approval; downloads also require permission and pinned artifact hashes. The actual worker rechecks authority and receives permissions with its retained in-memory request. System utilities, shared storage and PowerShell modules use trusted OS/machine settings rather than inherited path/module variables. Current policy support is partial: managed native-argument assets and service-host authorization are blocked. Native enrollment, update, rotation and signed recovery are implemented but still require the documented endpoint/deployment qualification. An active job retains its authenticated policy identity and validity window; its context is canceled when the one-second monitor observes policy change/removal/enrollment, expiry or an unreadable authority. Cancellation uses the owned worker's termination path; it does not prove that every external vendor side effect has been rolled back.
