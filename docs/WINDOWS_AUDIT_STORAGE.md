# Windows audit storage and desktop qualification

The Windows amd64/arm64 source candidate connects public local initialization, current-stream recording and historical export to the protected NTFS backend. It uses the existing event/checkpoint format and recorder contracts. Storage, bound input/output identities and genuine ordinary-process prerequisites have the source-built native qualification below. Real CLI/UI/foreground-run and signed managed required-audit acceptance are being qualified in the same public-entry-point candidate; their dual-architecture results remain pending. This work does not close the enterprise audit readiness gate.

## Storage and commit contract

The storage boundary accepts an existing private directory on a fixed local NTFS volume with persistent ACL support. It opens the drive root and each single path component through retained native handles; child files open relative to the final handle. Ancestor bindings remain open without delete sharing. Canonical local paths, non-reparse objects, full volume/file identities, one-link regular files, bounded sizes and handle-based security checks are required. Device/UNC paths, alternate-stream inputs, ambiguous components and unsupported storage refuse.

The final directory, `.actor-key` and `events.journal` require the executing SID as owner and a protected private DACL granting access only to that owner and SYSTEM. Ancestors permit unrelated read access but restrict replacement and permission-changing authority to trusted principals. Same-account processes, SYSTEM and privileged administrators remain trusted; external engines share their executing account's authority. Other unprivileged accounts must be excluded from key access. Independently authenticated genesis/head checkpoints remain essential because local hashes do not authenticate trusted local writers.

Initialization requires an empty directory and exclusively creates both files with private descriptors already attached. Writable handles use `FILE_WRITE_THROUGH` and synchronous native I/O. Exact offset writes and `File.Sync` (`FlushFileBuffers`) precede key readback or complete candidate-journal verification, binding/size checks and any returned successor. Current opening and every append recheck the retained key and OS/build producer. Changed key, SID, elevation, build or target requires independent reenrollment with the previous stream retained.

Microsoft's [file-caching guidance](https://learn.microsoft.com/en-us/windows/win32/fileio/file-caching) describes cached metadata and flushing; [CreateFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) documents write-through requests, including NTFS metadata, and [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers) documents the file-buffer flush. These are OS persistence requests. The implementation makes no directory-fsync claim; live readback, successful close and process interruption do not establish reboot, power-loss or hardware durability qualification.

A writer holds an exclusive nonblocking journal byte-range lock for its lifetime and serializes operations. Short/failed writes, flush failures and uncertain postwrite checks return no successor, poison the handle and preserve every byte. Existing permissions, partial initialization and unknown tails are never repaired, truncated, deleted, retried or silently adopted. Reopening requires both independently retained endpoints; a complete uncertain tail needs independent reconciliation. Native calls may block beyond context deadlines. Close waits for active work, attempts all owned closes and retains its first error.

## Historical export

Historical export obtains a shared nonblocking lock excluding writers, verifies the complete bounded snapshot against both supplied endpoints, and closes source handles before emitting canonical event JSONL. It performs no flush or storage repair and requires neither key contents nor a producer matching the current build. Direct regular-file outputs are compared against journal and optional key identities. The metadata-only key probe may refuse when an existing key ACL prevents the required metadata access; it never reads key data. Callers must also protect checkpoint inputs and forwarded output destinations.

## Connected input and output identity checks

The command layer now retains the native object identity from each actual bounded input read and rechecks that name before output admission. Pairwise output checks protect checkpoints, profile/policy inputs, journal/key files and the engine's resolved executable/configuration/coordination files. Cached identities also protect an old input object after its original name is replaced. Windows uses the full 64-bit volume and 128-bit FileIdInfo identifier; Unix uses native device/inode metadata. These comparisons do not authenticate input contents or grant authority.

Windows metadata probes open no data stream, repair nothing and resolve only bounded ordinary local disk paths. Device/UNC/extended namespaces, remote reparse targets and unsupported providers refuse. Borrowed pipe/character outputs retain their existing forwarding contract; direct disk outputs require an available local native identity. Source input reads still require a regular, unchanged bounded snapshot. The native storage layer retains its separate NTFS, ACL, one-link and binding checks. Fixed Windows managed authority remains the protected 64-bit HKLM values; generic commands no longer probe Linux /etc paths on Windows. Recorded policy producers remain Linux-only.

## Ordinary process qualification fixture

A separate exact-opt-in hosted fixture now prepares a fresh ordinary account and a genuine process with its own loaded profile. Before resume it checks the primary token, native architecture, staged image identity/hash, fresh profile binding and held process job. A private desktop and PID-bound local pipe isolate the worker; pending native I/O retains pinned buffers until completion. The worker checks its native profile/HKCU/cache, isolated console cancellation and the public unsupported-recording result. Teardown rechecks profile/staging identities and account binding, then verifies process, profile, account and handle cleanup; ambiguous objects are preserved and fail the job. The bounded prelaunch profile-directory inventory excludes preexisting profile names and identities from cleanup eligibility.

The retained c3e70de fixture qualifies process/profile/cleanup prerequisites without policy enrollment or product writes; public recording was unsupported in that source revision. These results cover this prerequisite fixture with public recording disabled. The containing [CI run](https://github.com/Yunushan/accessweaver/actions/runs/41945002196) passed all 24 jobs. ## Using a Windows private directory

Local recording requires an existing empty private directory on persistent local NTFS. Its owner must be the executing user SID, with a protected DACL granting full access only to that SID and SYSTEM; the descriptor shape is `O:<user-SID>D:P(A;;FA;;;<user-SID>)(A;;FA;;;SY)`. Provision a new directory under trusted ancestry before initialization. Existing directories, permissions and uncertain journal bytes are not repaired. Run user commands as the normal desktop account; a stream cannot migrate between accounts, elevation states or builds by changing its owner or key.

Use the same documented command arguments with Windows paths, and preserve native UTF-8 checkpoint/event bytes in distinct new output files. Initialize/import/UI/current export and foreground run are the public candidate scope. Recorded policy install/update/rotation/recovery remains Linux-only; Signed installed-product and managed-endpoint enrollment qualification remain separate acceptance work.
