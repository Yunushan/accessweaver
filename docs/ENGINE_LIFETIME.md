# Engine lifetime and recovery

A successful launch returns a handle for that exact engine run. Launch acceptance does not establish routing, service readiness or completion. Canceling a handle wait only cancels that wait; explicit shutdown requests stopping the owned launch. An unavailable native exit observer refuses process creation, although preparation may already have written generated inputs.

On Linux, macOS, FreeBSD and OpenBSD, each foreground engine starts a new session with its initial process group. A single per-launch owner serializes signals against the consuming process wait. Normally it observes leader exit without reaping, attempts final cleanup of the original group, closes signal admission, then performs the sole process wait and drains output. A failed observer with retained identity instead attempts forced cleanup and records lifecycle uncertainty. Natural leader exit triggers immediate final group-signal dispatch; it does not prove every member terminated or classify the run as a manually accepted stop. Manual shutdown retains its graceful interval while the leader remains alive; natural leader exit can shorten that interval for descendants. The existing two-second owned-pipe drain budget is independent of policy cancellation and cannot bound an arbitrary blocked output destination Write.

This contract relies on exclusive child-status ownership: AccessWeaver must not install automatic child reaping or introduce another component that consumes this child's wait status. The session prevents an unrelated process from joining the original group. An engine can move descendants into another group or session, change privileges or create persistent external state. Those effects need stronger OS containment or the vendor's recovery procedure and are outside original-group cleanup.

If final cleanup cannot be confirmed while ownership is retained, the manager exposes a fixed pending error and refuses a replacement launch. The exact handle remains pending. The desktop shows “Shutdown unconfirmed” and disables launch controls while profile editing, logs and support inspection remain available. The in-process `Manager.RetryCleanup` operation requires that same current handle and explicitly retries cleanup only while the original identity remains owned. The CLI does not retry automatically. If exclusive ownership is lost, numeric process identity cannot safely be recovered: no further signals, consuming waits, releases or cleanup retries are issued for that identity.

The foreground CLI keeps waiting for the exact run after cancellation, a failed launch notice or a stop error. Repeated manager shutdown calls share one worker and terminal result: a caller deadline cancels only that caller’s wait, while the worker retains the exact active generation and drains it after the single stop attempt. It emits fixed local feedback when shutdown is unresolved. Desktop server shutdown closes new request admission, starts engine shutdown before waiting on admitted handlers, and retains the server scope until those handlers, HTTP serving and the shared engine shutdown finish. A diagnostic shutdown budget or fixed pending fault can produce a waiting notice; it cannot release controller/runtime ownership. Startup-output and listener failures follow the same drain path, and a failed/short waiting notice is returned only after that drain. Scoped pipe-signal observation prevents a broken stdout/stderr pipe from skipping cleanup. Recorded foreground runs also retain their journal and controller owners until actual terminal observation. A permanently unresolved run can therefore keep the command active indefinitely. Forcing the controlling process to exit abandons that observation and requires independent operator reconciliation; it is not proof that engine or vendor state was removed.

Actual child wait status, policy revocation and lifecycle uncertainty remain separate result fields. Lifecycle uncertainty prevents a successful recorded terminal outcome even if the child exited with status zero. Audit output contains only the fixed indeterminate outcome, with no native error text. Windows retains its existing process-handle termination behavior. Workflow/vendor shutdown still uses its separate bounded wait; this engine/HTTP ownership change does not establish complete workflow cleanup or recovery of external vendor state.

Source tests and cross-compilation validate specific contracts. Native Linux/macOS CI and separate FreeBSD/OpenBSD runtime qualification are required for their respective observer paths. These checks do not establish installed-product acceptance, escaped-descendant containment or a completed enterprise readiness gate.
