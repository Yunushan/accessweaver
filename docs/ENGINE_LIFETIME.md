# Engine lifetime and recovery

A successful launch returns a handle for that exact engine run. Launch acceptance does not establish routing, service readiness or completion. Canceling a handle wait only cancels that wait; explicit shutdown requests stopping the owned launch. An unavailable native exit observer refuses process creation, although preparation may already have written generated inputs.

On Linux, macOS, FreeBSD and OpenBSD, each foreground engine starts a new session with its initial process group. A single per-launch owner serializes signals against the consuming process wait. Normally it observes leader exit without reaping, attempts final cleanup of the original group, closes signal admission, then performs the sole process wait and drains output. A failed observer with retained identity instead attempts forced cleanup and records lifecycle uncertainty. Natural leader exit triggers immediate final group-signal dispatch; it does not prove every member terminated or classify the run as a manually accepted stop. Manual shutdown retains its graceful interval while the leader remains alive; natural leader exit can shorten that interval for descendants. The existing two-second owned-pipe drain budget is independent of policy cancellation and cannot bound an arbitrary blocked output destination Write.

This contract relies on exclusive child-status ownership: AccessWeaver must not install automatic child reaping or introduce another component that consumes this child's wait status. The session prevents an unrelated process from joining the original group. An engine can move descendants into another group or session, change privileges or create persistent external state. Those effects need stronger OS containment or the vendor's recovery procedure and are outside original-group cleanup.

If final cleanup cannot be confirmed while ownership is retained, the manager exposes a fixed pending error and refuses a replacement launch. The exact handle remains pending. The desktop shows “Shutdown unconfirmed” and disables launch controls while profile editing, logs and support inspection remain available. The in-process `Manager.RetryCleanup` operation requires that same current handle and explicitly retries cleanup only while the original identity remains owned. The CLI does not retry automatically. If exclusive ownership is lost, numeric process identity cannot safely be recovered: no further signals, consuming waits, releases or cleanup retries are issued for that identity.

The foreground CLI keeps waiting for the exact run after cancellation, a failed launch notice or a stop error. Repeated manager shutdown calls share one worker and terminal result: a caller deadline cancels only that caller’s wait, while the worker retains the exact active generation and drains it after the single stop attempt. It emits fixed local feedback when shutdown is unresolved. Desktop server shutdown closes new request admission, starts engine and workflow shutdown before waiting on admitted handlers, and retains the server scope until those handlers, HTTP serving and both manager completions finish. A diagnostic shutdown budget or fixed pending fault can produce a waiting notice; it cannot release controller/runtime ownership. Startup-output and listener failures follow the same drain path, and a failed/short waiting notice is returned only after that drain. Scoped pipe-signal observation prevents a broken stdout/stderr pipe from skipping cleanup. Recorded foreground runs also retain their journal and controller owners until actual terminal observation. A permanently unresolved run can therefore keep the command active indefinitely. Forcing the controlling process to exit abandons that observation and requires independent operator reconciliation; it is not proof that engine or vendor state was removed.

Actual child wait status, policy revocation and lifecycle uncertainty remain separate result fields. Lifecycle uncertainty prevents a successful recorded terminal outcome even if the child exited with status zero. Audit output contains only the fixed indeterminate outcome, with no native error text. Windows retains its existing process-handle termination behavior. Workflow worker completion and external vendor recovery remain separate observations.

Source tests and cross-compilation validate specific contracts. Native Linux/macOS CI and separate FreeBSD/OpenBSD runtime qualification are required for their respective observer paths. These checks do not establish installed-product acceptance, escaped-descendant containment or a completed enterprise readiness gate.

Workflow shutdown captures the job reserved or active at its first call, including admission and final status persistence. Its eight-second desktop diagnostic budget does not release that job; the server rejoins its completion without a deadline. The system workflow CLI follows the same rule after cancellation, emits fixed waiting feedback if needed, and prints the actual final snapshot after the worker returns. A failed or short waiting notice also retains this scope until completion. Startup and shutdown pipe output remain protected while work is owned.

The workflow result retains admission, execution, result validation, persistence and native cancellation failures independently of the bounded display text in Job.Error. Repeated shutdown calls return the captured generation's same final error, including a final-save failure. The printable error lists fixed stage labels; local callers can inspect underlying causes without placing raw private tool errors on stderr. An inactive historical failure is not adopted as a new shutdown failure. Plain explicitly requested cooperative cancellation can finish without an additional shutdown error only when result validation and persistence also succeed; the job's original outcome is preserved.

The command cancellation observer records the configured callback's result without changing its target or native behavior. This prevents a process ExitError from hiding a failed termination helper. Worker completion still does not certify vendor rollback, every descendant's exit, persistent services or external machine state. A failed final save can leave the previous running record on disk while the in-memory job and shutdown report failure; preserve that evidence and reconcile it rather than retrying automatically.
