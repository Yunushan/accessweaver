# Windows installer preservation diagnostics

The disposable hosted installer fixture preserves its original selected service, firewall and DNS baseline. All fifteen observations and thirty baseline/transition comparisons remain required. A successful uninstaller does not establish preservation: the final strict state comparison must also pass. No rule is exempted, deleted or adopted as a new baseline by these diagnostics.

## Existing event records after drift

When a failed fixture has captured a firewall identity change, it may start one isolated Windows PowerShell child to read the existing local channel Microsoft-Windows-Windows Firewall With Advanced Security/Firewall. Successful unchanged runs do not query event logs. This is test-fixture diagnostics, not a shipping product logger.

The query uses the UTC interval from immediately before the initial state snapshot to collection after failure, capped at two hours. It requests at most 129 records, examining the first 128 and treating the extra record as a limit sentinel. The child has a requested ten-second process wait timeout through the existing sanitized process helper. Output draining and owned-process cleanup retain their existing separate bounds; blocking native startup/I/O is not given a hard whole-command deadline. No event channel, audit policy, firewall rule or system logging configuration is enabled or changed.

The parser accepts Windows event XML using the documented [event schema](https://learn.microsoft.com/en-us/windows/win32/wes/eventschema-schema). It limits each event to 65,536 UTF-8 bytes, prohibits DTDs and external resolution, rejects ambiguous sections or named fields, and checks the exact provider/channel and UTC interval. It matches an event only when its named RuleId value has the same exact SHA-256 fingerprint as a captured changed rule identity. It does not assume a particular numeric event ID or normalize identities to manufacture a match. Missing fields, version differences, case differences, unavailable/disabled logs, overwritten records or caps can prevent correlation; absence of a match proves no origin.

At most sixteen matching records are retained. Each contains the identity fingerprint, observed event/record IDs, UTC time, a fixed modifying-application basename class, and presence/length/hash metadata for ModifyingApplication, ModifyingUser, ApplicationPath, ServiceName and Origin when present. Each field is capped at 4,096 UTF-8 bytes; excessive values are marked omitted. Raw XML, rule names, account identifiers, paths, command lines, event descriptions and native error text are excluded. Large event record IDs remain decimal strings to avoid JSON integer precision loss.

A named event field or basename class is an observation, not verified image identity, human attribution, process lifetime evidence or proof that AccessWeaver caused a change. processOriginEstablished remains false. Full logs are never copied into the report. Query errors, incomplete capture, stale returned windows and malformed output produce fixed unavailable metadata without replacing the original installer failure or the last uninstaller attempt.

Microsoft documents the supported [filtered Get-WinEvent reads and MaxEvents parameter](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.diagnostics/get-winevent?view=powershell-5.1) and [DTD processing controls](https://learn.microsoft.com/en-us/dotnet/api/system.xml.xmlreadersettings.dtdprocessing). The helper conditionally consumes named fields actually present in a record; these references do not guarantee every Windows build emits them or that a log is complete.

## Source binding and validation

Native report schema 11 includes the event-helper source digest and a separate firewallEventDiagnostics envelope. The existing captured-object firewallOriginDiagnostics still performs no extra firewall-rule query. A passing report must have the exact empty not-needed event envelope with zero queries, while retaining all original state, lifecycle, cleanup and uninstaller-deadline assertions. The independent verifier checks the new helper digest and rejects missing, extra, mutated, private or unbounded metadata. Earlier schema-10 failures remain historical evidence rather than new-schema acceptance.

The pure PowerShell tests use synthetic XML and injected readers/child responses only. They inspect the actual fixture adapter through AST import, validate its encoded child syntax and quoted path handling, and confirm it preserves the original uninstaller attempt. They cover provider/channel/time/identity mismatch, unknown numeric event IDs, DTD/entity attempts, malformed/duplicate sections and fields, character/UTF-8 limits, event/record caps, unavailable/partial/stale child output, and PowerShell 5.1-string versus 7 UTC-DateTime JSON behavior. Local Windows PowerShell 5.1 execution policy is not bypassed; fresh hosted pure/native results remain necessary.

The schema-11 definition and local synthetic tests do not establish a native query result or explain previous firewall drift. Inspect exact new hosted source-bound evidence. A later pass is not a diagnosis or remedy for the earlier strict preservation failure. Full publisher signing, installed-product, reboot, managed endpoint and vendor/network qualification remain separate.
