# Portable build provenance

The hosted release workflow builds the ten portable core archives twice, compares the complete checksums, and generates one signed GitHub/Sigstore build-provenance bundle covering twelve subjects: ten archives, `BUILD-MANIFEST.json` and `SHA256SUMS.txt`. The retained `BUILD-PROVENANCE.sigstore.json` is the thirteenth distribution file. It cannot checksum or attest itself; its certificate/signature and transparency evidence are verified through the trusted Sigstore roots used by GitHub CLI.

The action is `actions/attest` v4.2.2 pinned to commit `1e69f48acb82d1966a394da916b4c1698aa569d6`. Only the packaging job has `id-token: write` and `attestations: write`; ordinary test jobs retain read-only permissions. There is no long-lived signing key, custom predicate, registry upload or unsigned fallback. A signing or verification error prevents release artifact upload/publication. [GitHub's attestation documentation](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations) describes the identity/certificate mechanism and repository-plan requirements.

## Verify a downloaded candidate

Use a trusted, supported GitHub CLI that implements all flags used by `scripts/verify_release_provenance.py`, together with Python 3 and the verifier from the reviewed candidate source commit. Later verifiers may require newer inventory/content contracts and reject older alpha archives; use the approved candidate version rather than removing checks. Missing tools, unsupported flags, unavailable trust services or verification failures stop acceptance; do not remove constraints to make verification pass. The archive download must be in a private directory containing only the thirteen release files. Do not extract or run a downloaded executable first.

Obtain the expected full source commit and complete ref from your independently approved release record. Do not copy these trust choices from an unverified manifest or bundle. For an approved release tag, run:

```text
python scripts/verify_release_provenance.py DOWNLOADED_DIRECTORY --source-commit FULL_TRUSTED_COMMIT --source-ref refs/tags/APPROVED_VERSION_TAG
```

A manual preview uses its independently recorded commit and `refs/heads/main`. The verifier pins all of the following:

- repository `Yunushan/accessweaver` and host `github.com`;
- signer workflow `Yunushan/accessweaver/.github/workflows/release.yml`;
- both source and signer-workflow digests to the approved commit;
- the exact approved source ref;
- OIDC issuer `https://token.actions.githubusercontent.com`;
- SLSA provenance v1 predicate and GitHub-hosted runners;
- each artifact's actual digest, through the signed bundle.

The manifest is authenticated before it chooses which archive names to inspect. The portable integrity verifier checks the complete file set and inspects private archive copies after digest validation. It checks ZIP and tar members for bounded sizes and counts, portable names, and file or directory collisions before reading the archived executable and its metadata. Its optional native metadata probe runs only after every target has passed the content checks. Exactly the ten documented targets must appear, and the source state must be clean. After authenticating every subject, the verifier runs the existing archive/checksum/content/embedded-identity checks with binary execution disabled. It never treats checksums alone, an action summary or an attestation-shaped JSON file as signature verification. The compatibility `verify-release.py` integrity command remains available, but does not authenticate provenance by itself.

For one subject, the underlying [GitHub CLI verification command](https://cli.github.com/manual/gh_attestation_verify) is:

```text
gh attestation verify ARTIFACT --bundle BUILD-PROVENANCE.sigstore.json --hostname github.com --repo Yunushan/accessweaver --signer-workflow Yunushan/accessweaver/.github/workflows/release.yml --source-digest FULL_TRUSTED_COMMIT --signer-digest FULL_TRUSTED_COMMIT --source-ref FULL_TRUSTED_REF --cert-oidc-issuer https://token.actions.githubusercontent.com --predicate-type https://slsa.dev/provenance/v1 --deny-self-hosted-runners --format json
```

A retained bundle supports verification without downloading the attestation again, but trust-root material may still need network access/cache. Fully air-gapped trust-root provisioning/refresh remains work. GitHub documents that bundle-only name checks cannot detect later repository/owner renames or name reuse. Independently pinned commits/refs and organizational repository/ownership controls remain necessary.

Packaged acceptance requires the exact ordered eleven Unix controller checks and nine diagnostic name/path/transport tuples. Successful reports must use the producer's closed schema, expected native platform and a valid binary digest. Controller results match the authenticated executable digest; diagnostic source, build and binary identities remain bound to the staging receipt. Missing, duplicated, reordered, unknown or altered cases and unexpected fields refuse acceptance. This report validation still requires fresh runtime evidence for the actual candidate.

Publication depends on all six packaged native jobs, both packaged FreeBSD guest jobs and both packaged OpenBSD guest jobs as well as packaging. A manual preview still creates no release. These checks execute the actual stripped, trimpath, CGO-disabled portable cores, rather than substituting a separate test build. ## Remaining signing and trust requirements

The manifest's `unsigned: true` and the unsigned-alpha artifact labels still describe the OS binaries. Build provenance identifies a GitHub workflow and source; it does not provide Windows Authenticode, macOS Developer ID/notarization, an installer signature or authenticated in-product update selection. Publisher certificates, signing-key ownership, deployment application control and those native distribution checks remain required.

On Windows, verify each signed executable or MSI before deployment using an independently approved SHA-256 for the final signed artifact and the SHA-256 fingerprint of the organization's leaf code-signing certificate in DER form. Run this in a private candidate directory from the approved source checkout.

```powershell
.\scripts\verify-windows-installer-publisher.ps1 -Artifact SIGNED_ARTIFACT -ArtifactSHA256 APPROVED_ARTIFACT_SHA256 -PublisherCertificateSHA256 APPROVED_CERTIFICATE_SHA256
```

The verifier requires a Windows-valid embedded Authenticode signature, a timestamp certificate and the exact approved publisher fingerprint. It holds a read-only handle while checking the file and returns a fixed JSON receipt with the two digests. The check covers the supplied file. Verify the signed setup and shipped executable payload individually. Retain separately authenticated provenance covering the final signed bytes and the approved signing handoff. The existing unsigned-alpha attestation covers the unsigned candidate. An approved organization signer and signed candidate are still required for native acceptance. [Windows Authenticode verification](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.security/get-authenticodesignature).

On an organization-controlled Windows build host, invoke the existing Inno build with the approved organization signer executable. The signer accepts one artifact path, signs it in place with a trusted timestamp, and exits nonzero on failure. Configure its provider and credentials on that host. The build signs the payload before packaging, and the Inno callback checks the approved publisher on setup and its generated uninstaller. Each signing operation compares the signed PE to the original, including the installer payload beyond the PE sections. It allows the checksum, certificate-directory fields, zero alignment padding and appended certificate table to change. [Microsoft PE format](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#the-attribute-certificate-table-image-only). Signed output and build evidence are kept in a new per-build directory under the build directory. A clean source checkout is required.

```powershell
.\scripts\build-windows-installer.ps1 -Compiler APPROVED_ISCC_EXE -Version RELEASE_VERSION -TargetArch amd64 -SigningTool APPROVED_SIGNER_EXE -PublisherCertificateSHA256 APPROVED_CERTIFICATE_SHA256
```

Repeat the build for ARM64. Authenticate the final signed output and its provenance, then exercise installation, upgrade, reboot and signed uninstall on both managed Windows architectures before promotion. [Inno Setup signing](https://jrsoftware.org/ishelp/topic_setup_signtool.htm).

For a signed macOS flat package, place the final stapled package alone in a private directory. Supply its independently approved SHA-256, Developer ID Team ID and SHA-256 fingerprint of the approved Developer ID Installer leaf certificate.

```sh
python3 scripts/verify_macos_installer_publisher.py PRIVATE_PACKAGE_DIRECTORY --artifact-sha256 APPROVED_PKG_SHA256 --team-id APPROVED_TEAM_ID --publisher-certificate-sha256 APPROVED_CERTIFICATE_SHA256
```

The verifier checks the digest before invoking macOS signature tools on a private copy. Check the signed application payload's Developer ID Application identity and validate installation on the supported native matrix. [Apple's packaging and notarization guidance](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution).

Use a clean checkout and the native Go SDK. The build signs the application before sealing its detached manifest and compiled SBOM. It signs the package helper before copying it into both installer phases. After checking the package's signer and verifying Apple's accepted notarization and stapled ticket, it expands the signed package and compares its payload and script inventories against the sealed build.

python3 scripts/build-macos-deployment.py --architecture arm64 --version RELEASE_VERSION --application-identity APPROVED_APPLICATION_IDENTITY --installer-identity APPROVED_INSTALLER_IDENTITY --team-id APPROVED_TEAM_ID --publisher-certificate-sha256 APPROVED_INSTALLER_CERTIFICATE_SHA256 --notary-keychain-profile APPROVED_PROFILE

Repeat on Intel with amd64. Signed build output is under the build/macos-signed-deployment directory. The build records the final stapled package digest and generates its SBOM from the signed bytes. The package remains a versioned deployment candidate. Its launcher integration, final signed-byte provenance, and native installation and lifecycle evidence remain required. Copy the builder's evidence/payload.exe and payload-SBOM.cdx.json as accessweaver-VERSION-windows-ARCH.exe and accessweaver-VERSION-windows-ARCH.exe.cdx.json. For each Mac architecture include the final stapled versioned package and its CycloneDX SBOM. The version in these filenames omits the tag's leading v.

Verify native publisher signatures and the build-source evidence before approving the inventory. The manifest tool checks all six CycloneDX sidecars against the final artifact bytes, release version, clean source commit and target. It also checks that each Windows installer sidecar describes the matching signed payload. For each macOS target it also requires the compiled helper identity to match the release and both package script entries to carry the same helper SHA-256. Verification repeats these checks on the authenticated files and reports the number of SBOM bindings verified. The `macosDetection` result supplies the matching package and detector digests for each architecture. Write SIGNED-RELEASE.json outside the input directory. Sign its exact bytes through the organization's approved release-approval certificate and signer using detached DER CMS. Give verifiers the public certificate as a DER file and its SHA-256 fingerprint through the same independently controlled channel as the approved commit and tag. The certificate must stay outside the candidate directory.

```text
python scripts/signed_release_manifest.py prepare PRIVATE_CANDIDATE --output APPROVAL_DIRECTORY/SIGNED-RELEASE.json --source-commit FULL_APPROVED_COMMIT --source-ref refs/tags/APPROVED_TAG
openssl cms -sign -binary -md sha256 -in APPROVAL_DIRECTORY/SIGNED-RELEASE.json -signer APPROVED_PUBLIC_CERTIFICATE_PEM -inkey APPROVED_SIGNING_KEY_REFERENCE -outform DER -out APPROVAL_DIRECTORY/SIGNED-RELEASE.p7s
```

Use the organization's signing service or configured OpenSSL provider to supply the key reference. The manifest tool takes no private-key input. Copy the manifest and signature beside the twelve subjects. Obtain the current revocation list and its SHA-256 fingerprint from the organization's release-control channel for each deployment. Keep the list outside the candidate directory. It uses this versioned format, with exact lowercase source commits or SHA-256 digests and complete release tag refs:

```json
{
  "schemaVersion": 1,
  "sourceCommits": [],
  "sourceRefs": [],
  "subjectSHA256": [],
  "approvalCertificateSHA256": []
}
```

Empty lists express an explicit decision by that channel that there are no active revocations. An approving or deployment operator should never construct an empty list as a fallback. After authenticating the current list and fingerprint through release control, run the deployment check.

```text
python scripts/signed_release_manifest.py verify PRIVATE_CANDIDATE --approval-certificate INDEPENDENT_APPROVAL_CERTIFICATE_DER --approval-certificate-sha256 APPROVED_CERTIFICATE_SHA256 --revocation-list CURRENT_REVOCATION_LIST --revocation-list-sha256 CURRENT_REVOCATION_LIST_SHA256 --source-commit FULL_APPROVED_COMMIT --source-ref refs/tags/APPROVED_TAG
```

The verifier checks the approval signature with the supplied certificate and compares the exact inventory, sizes and SHA-256 digests against the received bytes. It also refuses a revoked commit, tag, subject digest, macOS detector digest or approval certificate and records the revocation-list fingerprint in its result. Release control must distribute the latest list and fingerprint, and deployment operators must fetch them again before retrying or approving a cached candidate. An old list and its matching old fingerprint can still authenticate that older policy. Retain the separate build provenance, native publisher checks and installed-product results for that candidate. [OpenSSL CMS verification](https://docs.openssl.org/3.5/man1/openssl-cms/).

### Evaluate an authenticated managed update

Add `--current-version INSTALLED_VERSION --target windows/arm64` to the `verify` command above. Use the version and native target from trusted endpoint inventory. Supported targets are `windows/amd64`, `windows/arm64`, `darwin/amd64` and `darwin/arm64`. The `managedUpdate` result identifies the authenticated installer filename and digest for that target. An `upgrade` decision means the candidate is newer and follows the installed release channel. Stable installations decline prereleases. Prerelease installations can advance to a newer prerelease or stable version. Equivalent versions and older candidates return `current` or `older`. A stable installation presented with a prerelease returns `channel-mismatch`. The verifier makes no installation changes.

Add `--stage-directory TRUSTED_STAGING_DIRECTORY` to stage an eligible installer in an existing, separate directory on a filesystem that supports hard links, such as NTFS or APFS. The verifier copies from the authenticated snapshot, checks the staged digest and publishes the approved filename without replacing an existing file. Successful staging sets `managedUpdate.installerStaged` to true. An ineligible candidate or failed verification leaves the installer unpublished. Restrict writes to the staging directory and run the native publisher verifier against the staged installer before handing it to endpoint management.
