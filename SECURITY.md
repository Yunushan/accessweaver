# Security policy

AccessWeaver `0.1.0-alpha` is experimental. It is not an audited VPN, anonymity system, firewall or kill switch. The security boundary includes every external executable, configuration file and script that you choose to run.

## Reporting a vulnerability

Use [GitHub private vulnerability reporting](https://github.com/Yunushan/accessweaver/security/advisories/new) when enabled for the repository. If it is unavailable, open a minimal issue asking the maintainer for a private contact channel; do not publish exploit details, secrets or private logs. No response-time commitment or dedicated security team is currently advertised.

Please include the affected commit/version, OS/architecture, impact, and minimal reproduction. Distinguish an AccessWeaver flaw from behavior of a third-party engine. Only the current alpha is actively developed; there is no long-term-support release line.

## Implemented controls

- The UI/API binds to `127.0.0.1` on an ephemeral port. Every API request requires a random per-process token, including bootstrap and read requests. Allowed-host and browser-origin checks apply separately.
- The dashboard refuses elevated/root execution. An OS-private launch file delivers its credential through a URL fragment; the browser removes the fragment and retains the credential in session storage. Bootstrap does not disclose it. Ordinary local processes running as the same user remain trusted.
- Windows machine storage rejects unexpected owners, access controls and reparse points before reuse. Service-host reuse also verifies its digest against the running controller.
- Browser assets are local, with a restrictive content security policy and no third-party JavaScript or analytics.
- Profiles use versioned JSON, strict unknown-field rejection, request/file size limits and validated filenames. Saved files are atomically replaced with private modes where supported.
- Engine invocation uses argument arrays. Platform-specific executable basenames and optional SHA-256 pins are checked before launch.
- Preview explains the command and local readiness issues. Unsupported managed routing and known service/daemon options are rejected.
- Managed ByeDPI binds to loopback. WireSock command hooks are rejected, and supported external configuration paths must reference local regular files.
- Engine output is held in a bounded in-memory buffer rather than automatically persisted.
- CI and release packaging check known Go vulnerabilities across release targets with a pinned scanner. The gate rejects incomplete reports and affected imported packages; module-only advisories for unused packages remain visible. External engines and drivers require separate assessment.

These controls reduce particular attack paths; they are not a sandbox. An earlier 2026-11-01 review identified three local privilege-boundary findings; their remediation and native qualification remain subject to the recorded limits. A later Standard source audit of commit `fc778d60b688c0471fe3fca3d7045ffb3f39b9dd` completed on the same day with zero confirmed reportable findings under this policy's trust assumptions (scan `fe3b476c-682b-4fdd-b0d6-4cd59e28833c`). It covered 134 tracked text/source/configuration/test/documentation files, with two reference images visually inspected. No application execution or vendor/native behavior was validated by that static audit. A managed ByeDPI option-validation discrepancy and stale privilege guidance were retained for hardening; the audit does not certify later commits or production readiness.

The later Standard source review of commit `84b4009dd0a603aec789191eb65823068cfa2dc6` (scan `c4fcd168-c043-4b0b-9b96-1d8cc7454831`) covered all 331 tracked paths, including two visually inspected reference images. It retained one medium-severity finding: a preexisting inheritable cache ACL on macOS could grant another local account access to the dashboard credential despite private POSIX modes. Actual deployed ACLs and a native cross-account reproduction were not established by that offline audit. The subsequent launcher change uses descriptor-relative parent inspection and clears inherited ACLs on exclusively created objects before writing a credential. Its disposable native baseline/patched regression is defined in `scripts/test-darwin-session.sh`; inspect the exact source-bound hosted results before treating the fix as natively qualified. No readiness gate is promoted by this source audit or implementation alone.

## Known limits

Foreground engines inherit the controller's permissions. Running the controller elevated expands the impact of engine arguments, Lua scripts and configuration. Foreground executable checks do not authenticate a publisher; a matching basename proves nothing, and a hash is only as trustworthy as its source. Windows workflow downloads use allowlisted sources with digest or Authenticode checks, but this is not a complete supply-chain audit. File/configuration checks do not remove every time-of-check/time-of-use risk.

The loopback token protects against browser-origin attacks and unauthenticated access from other local accounts; it does not isolate processes with the dashboard user's permissions. Profiles and browser storage are not encrypted. The optional support summary uses explicit metadata fields and omits raw profile, log, result, error and session contents; it is a user-downloaded file, not telemetry, a complete log bundle or an audit trail. Use a private configuration directory; do not expose the control port, tunnel it to remote users, or treat it as a multi-user API. Cooperating processes on the same OS/local filesystem serialize profile access with an OS file lock. CLI foreground controllers and imports also hold an exclusive root controller lock. These controls require an intact lock file and do not coordinate manual file writes, older binaries, different configuration roots or unqualified network/cross-OS filesystems. Windows system workflows use a separate machine-wide mutex, which does not provide multi-user authorization or fleet policy.

Windows and Linux have partial signed machine-policy enforcement using a protected 64-bit HKLM value or root-owned fixed `/etc` file, independent of user configuration roots/environment. Linux uses descriptor-relative checks, persistent private writer coordination, synced atomic publication, bounded abandoned-stage cleanup and a fixed child environment; unqualified source filesystems and effective POSIX ACL writes fail closed. It guards profile mutations, diagnostics, foreground launches, reviewed workflow inputs and pinned component downloads. Invalid/unreadable policy fails closed. Managed service starts, generated inputs and native-argument assets are blocked until their authorization/protected staging is implemented. Cold-process environment tests and read-only native worker tests cover OS path/module selection. Windows initial installation and monotonic updates use native registry transactions with an effective administrator-token check and an independently pinned initial key. Planned key rotation binds old-key authorization to the exact prior policy state and the new key's signed higher revision, then commits trust and policy together. Damaged-state/emergency recovery, native deployment qualification, running-job revocation, OS application control, every native location and other platforms remain unqualified; this does not isolate arbitrary same-user code or replace a privilege-separated broker. See [managed configuration](docs/MANAGED_CONFIGURATION.md). The earlier source audit does not cover this implementation.

The Windows administrative handoff is incomplete: the ordinary dashboard cannot apply operations that require elevation. Preview exposes that requirement and blocks apply when the current process lacks authority; execution checks it again before job creation. A valid reviewed request can be exported as JSON for separately reviewed and confirmed elevated CLI execution. The file contains no session credential, plan ID or transferred approval, but may contain sensitive user-supplied paths/arguments and must be stored privately. This is not an elevation broker or signed authorization. Application install, removal and start now require an unelevated interactive desktop token, including guards on the direct PowerShell helpers. Their staging files and journals stay in the user workflow directory; they reject combined machine DNS changes. Combined Discord repair is blocked before machine initialization until a privilege-separated broker exists. Local dispatch contracts cover these safeguards; native elevated refusal and real application lifecycle qualification are still required before treating application maintenance as production-qualified.

The foreground manager owns a child, not arbitrary services or system state. Windows foreground stop uses process termination and does not guarantee vendor cleanup or descendant termination. Windows maintenance workflows separately manage owned services/tasks/firewall rules, preserve DNS/file state in protected journals, and refuse conflicting file recovery. Abrupt termination and external vendor installers can bypass or exceed that recovery. Service hosts and maintenance jobs have bounded process logs; complete history retention is not yet enforced. A stopped process may leave independently configured routes, proxies, drivers or network lock in effect. Signed distribution/updates, native mobile VPN isolation and service-level privilege separation are not implemented.

A successful direct diagnostic does not prove proxy use, DNS privacy, tunnel enforcement, UDP/QUIC coverage or anonymity. Imported profiles, referenced files and Lua scripts need review before use. Config files may contain secrets and powerful options even when the profile JSON does not.

AccessWeaver itself has no telemetry. Third-party engines may have their own network behavior, telemetry and licensing policies; see [THIRD_PARTY.md](THIRD_PARTY.md).
